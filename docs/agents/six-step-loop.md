# 问题处理六步流程

六步流程是执行闭环，不是任务入口。任务先在入口完成初步分级和路由；进入本流程后，重点是确认真实目标、控制执行偏移、验证业务结果。

## 入口前置

开始分析前，先做初步判断：

- 咨询/讨论：只回答或讨论，不强制留下六步记录。
- 小修小改：可压缩记录，但仍要说明目标、改动和验证。
- 常规优化/修复：执行完整闭环，记录可简写。
- 高风险任务：涉及部署、数据库、权限、财务、生产写入时，必须完整展开并保留回滚与证据。

方向型任务（如“优化某模块”“提升体验”“增强分析能力”“流程改造”）不得直接进入设计或开发。先通过问答确认：使用者是谁、要支持什么判断、当前哪里造成误判、这次边界是什么。

## 流程

1. 分析  
确认真实任务目标，而不是复述用户原话。区分用户现象、表层修复项和业务目标；必要时与用户多轮问答，直到能说明“谁在什么场景下借助系统做出什么更好的判断”。

2. 设计  
写出方案如何服务真实目标。常规和高风险任务需说明要改的文件、数据流、兼容策略、测试场景和回滚方式；小修小改可压缩为改动点和验证点。

3. 执行  
按设计小步修改，不混入无关重构。遇到新问题时先判断它是否阻塞真实目标；相邻问题只记录，不自动并入当前任务。

4. 验证  
验证真实目标是否达成，而不是只验证代码改动存在。前端用本地预览和关键交互；后端用 API；部署用线上 mtime、HTTP 文件、API 和日志。

5. 复盘  
记录分析是否找到真实目标、方案是否服务目标、执行是否被中途问题带偏、验证是否回到业务结果，以及可复用规则。无偏差时可一句话说明。

6. 继续发现  
检查相邻链路是否存在同类问题，并决定是否建新任务。继续发现不自动扩大当前任务，除非新问题阻塞真实目标。

## 验证失败回落

- 第 1 次验证失败：回到设计。
- 第 2 次验证失败：回到分析。
- 第 3 次验证失败：回到设计。
- 第 4 次验证失败：进入复盘，标记未完成。

## 完成标准

任务完成时必须留下与任务等级匹配的闭环痕迹。低风险任务可压缩表达；高风险任务必须完整记录。方向型任务只有在真实目标被确认后，才算完成分析阶段。
