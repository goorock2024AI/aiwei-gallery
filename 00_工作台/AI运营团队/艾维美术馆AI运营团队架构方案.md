# 艾维美术馆 AI 运营团队架构方案

更新时间：2026-07-21  
定位：为艾维美术馆建立一支“由人负责决策与对外承诺、由 AI 负责研究、组织、分析、生产和追踪”的协作型运营团队。

## 一、先明确：AI 在本项目中是什么角色

AI 不是虚拟员工替代人，也不是只会回答问题的聊天窗口。它应当是美术馆的**运营参谋部与执行中台**：把分散在项目文档、经营数据、内容素材和会议结论中的信息，持续转化为清晰的判断、可执行的任务和可复盘的结果。

人保留四类不可外包的权力：

1. 对外承诺：签约、报价、付款、公开发布、合作关系与品牌立场。
2. 经营取舍：预算上限、项目立项/暂停、资源优先级与人员安排。
3. 现场判断：安全、客户投诉、艺术品、供应商、突发事件的最终处理。
4. 数据授权：谁可以查看、修改、导出或删除经营与个人信息。

AI 承担四类高价值工作：

1. 结构化：维护项目台账、会议行动项、文档索引、数据口径和复盘档案。
2. 分析：识别经营异常、项目延期、预算偏差、应收风险和传播机会。
3. 生产：生成计划、预算框架、活动 SOP、招商材料、内容初稿和报告。
4. 追踪：按既定节奏提醒待办、核查状态、汇总决策事项；未经人确认不自行代表美术馆对外行动。

## 二、团队总结构

```text
馆长 / 经营决策人（最终决策与授权）
            |
AI 运营总协调（唯一入口、任务分派、事实核验、周月复盘）
  ├── AI 项目管理官（项目台账、节点、风险、会议）
  ├── AI 策展与展览执行官（展览、活动、作品、现场 SOP）
  ├── AI 商务与空间运营官（赞助、场租、报价、回款）
  ├── AI 经营数据与财务分析官（收入、日结、应收、预算）
  ├── AI 内容与观众增长官（内容、渠道、社群、转化）
  └── AI 系统与知识管理员（运营系统、数据口径、版本、文档）
```

第一阶段不建议一开始就启用多个互相独立、各自写入系统的自动化 agent。应以一个“AI 运营总协调”作为用户入口和总编排，专项角色以技能包（skill）方式被按任务调用。这样既有专业分工，也不会出现多人对同一事实各说各话。

## 三、核心角色说明

| AI 角色 | 服务对象 | 负责的结果 | 不可越过的边界 | 典型触发语 |
|---|---|---|---|---|
| AI 运营总协调 | 馆长、全体负责人 | 周项目看板、经营周报、月度复盘、待决策清单 | 不替代馆长做预算、立项、合同决定 | “本周怎么推进”“给我全馆经营情况” |
| AI 项目管理官 | 项目负责人 | 项目立项、倒排期、RACI、风险表、会议纪要 | 不把“待确认”写成“已确定” | “推进云南重彩画展”“整理项目台账” |
| AI 策展与展览执行官 | 策展、运营 | 策展执行包、作品/物料清单、布展与接待 SOP、展后复盘 | 不代替专业人员决定作品真伪、保险和布展安全 | “做展览倒排”“列布展清单” |
| AI 商务与空间运营官 | 商务、馆长 | 招商策略、合作漏斗、报价框架、权益表、应收跟踪 | 不自行报价、发合同、承诺权益或修改价格 | “做场地招租方案”“准备赞助提案” |
| AI 经营数据与财务分析官 | 运营、财务、馆长 | 日结核查、收入结构、预算/实际差异、应收账龄、异常提示 | 不记账、不退款、不改收入记录、不提供付款指令 | “分析本月收入”“为什么收入下降” |
| AI 内容与观众增长官 | 内容、运营、商务 | 内容日历、文案初稿、渠道策略、活动转化复盘、观众洞察 | 不未经审核发布；不虚构艺术史、艺术家或合作信息 | “安排国庆内容”“写公众号初稿” |
| AI 系统与知识管理员 | 系统、项目协调 | 版本记录、数据字典、文档索引、发布清单、权限建议 | 不在未授权情况下直接部署、删改数据或暴露密钥 | “检查数据口径”“准备上线清单” |

## 四、AI 运营总协调的工作协议

这是本项目的主角色，也是日常对话的默认身份。

### 输入

- 用户的自然语言请求、会议结论、负责人反馈。
- 项目登记库与专题文档。
- 腾讯云自建 API 的只读经营数据。
- 运营系统代码、发布记录和工作日志。

### 固定输出

每次涉及经营或项目管理的任务，尽量输出以下五部分中的必要部分：

1. 当前事实：已确认、待确认、存在冲突的信息分别列明。
2. 判断：机会、风险、偏差及其依据。
3. 行动：负责人、截止日期、交付物、验收方式。
4. 决策：需要馆长或项目负责人明确拍板的事项。
5. 归档：应更新到哪个项目台账、专题文档或工作日志。

### 六步工作法

沿用项目现有规则，但将输出物标准化为：

`分析 -> 设计 -> 执行 -> 验证 -> 复盘 -> 继续发现`

“继续发现”不是泛泛建议，而是必须检查相邻风险：例如做展览预算时，同时检查赞助回款、库存、票务容量和现场人力；做系统发布时，同时检查备份、权限、版本记录和真机流程。

## 五、专属 Skill 设置

技能不是按部门文件夹复制，而是按可重复、高频、需要明确流程的工作创建。建议分三批建设。

### 第一批：先建立的 5 个核心 skill（7月-8月）

| Skill 名称 | 用途与触发场景 | 必要参考资料 | 固定产出 | 读写权限 |
|---|---|---|---|---|
| `aiwei-operations-command` | 全馆评估、周计划、跨项目协调、经营复盘 | 基础状态、项目库、经营数据口径、周报模板 | 决策简报、周看板、行动清单 | 默认只读；经确认更新计划/日志 |
| `aiwei-project-governance` | 立项、排期、会议、风险、项目状态更新 | `registry`、项目字段规范、模板库 | 立项单、RACI、倒排表、会议纪要 | 可建议更新；写入须确认 |
| `aiwei-exhibition-delivery` | 策展项目、展览活动、现场执行与复盘 | 策展大纲、作品/供应商清单、展览 SOP | 展览执行包、物料清单、日程与复盘 | 只读/生成文档；不触碰合同与收银 |
| `aiwei-revenue-control` | 日结、收入分析、应收、预算偏差、经营异常 | API 数据字典、财务口径、日结模板 | 日结核查、周月经营报告、异常清单 | 只读 API；绝不写入财务数据 |
| `aiwei-content-growth` | 公众号、视频号、社群、活动传播、内容复盘 | 品牌口吻、内容档案、活动信息、渠道指标 | 内容日历、初稿、发布清单、转化复盘 | 草稿可写；发布必须人工确认 |

### 第二批：在核心流程稳定后再建（8月-9月）

| Skill 名称 | 建设前提 | 解决的问题 |
|---|---|---|
| `aiwei-space-commercial` | 空间报价、档期、合同口径统一 | 场租线索、报价、排期、回款容易脱节 |
| `aiwei-inventory-retail` | 系统已具备可靠库存与采购数据 | 文创 SKU、成本、补货、陈列和毛利管理 |
| `aiwei-partner-crm` | 合作伙伴字段和隐私规则确定 | 品牌、媒体、艺术家、供应商的关系维护 |
| `aiwei-system-release` | 发布、备份、权限流程落地 | 降低线上部署、数据安全与版本追踪风险 |

### 第三批：只在数据质量达标后建设（10月后）

| Skill 名称 | 触发条件 | 预期价值 |
|---|---|---|
| `aiwei-audience-insights` | 连续 3 个月渠道、票务、活动数据可用 | 观众分群、复购和活动产品优化 |
| `aiwei-business-forecast` | 收支、成本、应收、项目预算口径一致 | 现金流预测、项目盈亏预估和资源投放建议 |
| `aiwei-annual-programming` | 展览与合作档案至少沉淀一个周期 | 年度策展组合、淡旺季产品和资源排布 |

## 六、每个 Skill 的最小结构

所有专属 skill 使用同一套轻量结构，保持可维护而不堆砌规则：

```text
skill-name/
├── SKILL.md                 # 触发条件、工作步骤、边界、输出格式
├── agents/openai.yaml       # 面向用户的名称、简介与默认提示词
├── references/              # 按需读取的数据字典、业务规则、模板说明
└── scripts/                 # 仅放必须可重复执行的校验或汇总脚本
```

`SKILL.md` 只保留做事方法和边界；项目资料、数据表字段、品牌资料、模板细节放在 `references/`，避免一个 skill 变成难以维护的“百科全书”。

## 七、事实源与数据权限

### 1. 事实源优先级

| 事项 | 唯一事实源 | AI 的处理原则 |
|---|---|---|
| 项目状态、负责人、下一节点 | `registry` 与线上 `project_registry` 同步台账 | 发现不一致即标红，不能自行猜测哪个为真 |
| 收入、费用、库存、应收 | 腾讯云自建 API / 运营系统 | 仅从实时数据分析，不用手工文档覆盖系统记录 |
| 展览策展与执行细节 | 对应展览专题文档 | 将“草案”和“确认版”明确区分 |
| 内容原稿与发布记录 | `aiwei-content` 与 `content_posts` | 文案生成可快，发布日期和数据必须可追溯 |
| 系统版本与变更 | Git 提交、发布记录、工作日志 | “已部署未提交”一律标为版本风险 |

### 2. 现有口径冲突

项目规则中仍出现“Supabase project_registry / content_posts”与“腾讯云自建 API 已替代 Supabase”两种表述。正式启用 AI 团队前，应由系统负责人于 2026-07-24 前给出一份《数据源与写入权限清单》，明确：

- 每张表实际位于哪里，谁有读权限、谁有写权限。
- 哪些字段为人工确认字段，哪些可由系统生成。
- 本地 `registry` 与线上项目台账的同步责任人、同步频率和冲突处理方式。
- API 鉴权、备份、敏感信息脱敏和日志保留方式。

在清单确认前，所有 AI 角色默认使用只读模式；不得把 API 地址、密钥、个人资料或完整经营明细写入公开文档、内容稿或外部工具。

## 八、人与 AI 的协作闭环

```text
人提出目标 / 上传事实
        ↓
AI 总协调识别任务类型与风险等级
        ↓
调用专项 skill 生成分析、方案或草稿
        ↓
人工确认经营决定、对外内容和数据写入
        ↓
AI 更新台账 / 形成执行清单 / 检查遗漏
        ↓
周度复盘：结果、偏差、下一步、需决策事项
```

### 风险等级与授权

| 等级 | 示例 | AI 可做什么 | 人必须做什么 |
|---|---|---|---|
| 绿 | 文档梳理、会议纪要、公开资料初稿 | 直接产出草稿、建议文档更新 | 抽查或确认即可 |
| 黄 | 项目状态、预算草案、内容排期、合作名单 | 分析、生成提案、标注待确认项 | 确认事实、负责人和对外口径 |
| 红 | 报价、合同、付款、退款、数据删除、公开发布、系统部署 | 仅提供方案、检查清单和模拟结果 | 明确批准并由授权人执行 |

| 阶段 | 时间 | 目标 | 主要交付物 |
|---|---|---|---|
| 0. 定规矩 | 07-21 至 07-31 | 明确角色、事实源、权限和模板 | 本方案确认版、数据源清单、项目字段规范 |
| 1. 建中枢 | 08-01 至 08-15 | 启用总协调、项目治理、收入控制三个 skill | 周看板、日结核查、会议纪要开始稳定产出 |

| 3. 做经营闭环 | 10-01 至 10-31 | 接入空间商业、库存或系统发布 skill 的成熟模块 | 黄金周日报、展后 P&L、SOP 与复盘档案 |

## 十、首个版本的成功标准

到 2026-08-15，AI 团队不以“创建了多少 agent”衡量，而以以下结果衡量：

1. 馆长可以在 10 分钟内看懂所有活跃项目、下周关键节点、收入概况和待决策事项。
2. 云南重彩画展有唯一负责人、倒排期、预算版本、作品清单和风险表。
3. 每日营业数据能被核查，每周能解释收入变化，每月能形成可供决策的经营复盘。
4. AI 产出的任何涉及事实、价格、日期、合作方或经营数据的内容，都能追溯到来源并标注确认状态。
5. 没有 AI 在未授权下代表美术馆发布、承诺、支付、退款、删除数据或部署生产系统。

## 十一、需要馆长确认的三个设计决定

1. **AI 的服务范围：** 第一阶段是否只覆盖项目、展览、经营数据、内容与系统知识五类工作，不直接参与人事与私人事务。
2. **技能存放位置：** 建议先将专属 skill 存放在本项目仓库的 `.codex/skills/` 下，与项目文档和代码一起版本管理；确认稳定后再决定是否安装为用户级通用 skill。
3. **写入策略：** 建议第一阶段采用“AI 生成草稿 + 人确认后写入”的双确认模式；项目台账等低风险结构化资料，可在明确授权后逐步开放受限写入。
