# 运营数据管理系统腾讯云迁移复盘：问题与处理办法

> 整理日期：2026-08-17  
> 适用范围：艾维美术馆运营数据管理系统从 Supabase/海外服务迁移到腾讯云轻量服务器，并在后续上线迭代中形成的部署、数据、网络和运维经验。

---

## 一、迁移背景

原系统依赖 Supabase 云端 PostgreSQL 与前端 Supabase SDK。迁移前的核心问题是：Supabase 海外服务在国内访问不稳定，影响前台收银、数据录入和日常运营。

最终采用的方案是：

- 腾讯云轻量应用服务器 Ubuntu 22.04。
- Docker Compose 部署 3 个核心容器：Nginx、Node.js REST API、PostgreSQL 17。
- 前端继续保持纯 HTML/CSS/JS。
- 后端由自建 `server.js` 提供 Supabase 风格的 `/rest/v1/{table}` API。
- 数据从 Supabase 读取后迁入腾讯云自建 PostgreSQL。

截至 2026-08-15，正式访问入口已切换为 `https://iwe.ucanart.cc`，由宿主机 `wechat-gateway` 承接 80/443，再反代到运营系统容器。

## 三、迁移中遇到的问题和处理办法

### 1. Supabase 国内访问不稳定

**现象**

系统依赖的 Supabase 海外服务在中国大陆访问不可控，直接影响业务录入。

**处理办法**

采用自托管轻量方案：

- PostgreSQL 17 承接数据库。
- Node.js 自建 REST API 模拟原 `/rest/v1/{table}` 调用方式。
- 前端 `store.js`、`auth.js` 从 Supabase SDK 改为请求自建 API。

**沉淀**

简单业务系统不需要完整自托管 Supabase。当前系统更适合“自有 Node API + PostgreSQL”，资源占用低、可控性更好、月成本约 34 元起。

### 2. 数据迁移时 JSONB 字段写入异常

**现象**

Supabase 返回的数据中包含空数组、对象数组等 JSONB 字段。迁入自建 API 时，如果只做浅层字段转换，JSONB 内容不能正确写入 PostgreSQL。

**处理办法**

- 修复 `server.js` 的 `toSnake` 逻辑，使其递归处理 JSONB。
- `revenue` 表数据量和字段较复杂，最终采用 SQL 直导，绕过 API 层 JSONB 处理限制。
- `users`、`app_config`、`operation_logs` 继续通过 REST API 逐条 POST。

**沉淀**

迁移 JSONB 数据时，不能只验证接口 200；必须核对数据库落地后的 JSON 结构、数组字段和前端读取效果。

### 3. PostgreSQL NUMERIC 返回字符串

**现象**

Node `pg` 驱动读取 PostgreSQL `NUMERIC` 字段时默认返回字符串，前端统计和金额计算容易出现字符串拼接或小数展示错误。

**处理办法**

- 后端对金额字段做显式数值转换。
- 后续支出 PDF、图表统计等模块统一增加金额解析函数，避免隐式类型转换。

**沉淀**

所有金额字段都按“数据库 NUMERIC、接口 number、展示保留两位小数”的口径处理。新增金额字段时要同步检查白名单、模型和统计逻辑。

### 4. HTTP 环境下 `crypto.subtle` 不可用

**现象**

旧前端登录逻辑依赖浏览器 `crypto.subtle.digest()` 做密码哈希，但该 API 在非安全上下文中不可用。迁移初期入口是 HTTP IP，导致登录逻辑存在环境限制。

**处理办法**

- 登录改为服务端接口 `/rest/v1/login`。
- 密码校验由 Node.js 后端完成。
- 2026-08-15 接入 HTTPS 域名后，前端 API base 改为 `window.location.origin`，避免 HTTPS 页面请求旧 HTTP IP。

**沉淀**

认证、密码哈希等能力不应放在依赖浏览器安全上下文的前端逻辑中。正式域名启用 HTTPS 后，前端必须使用同源 API，避免 mixed content 和旧入口漂移。

### 5. Nginx `proxy_pass` 末尾斜杠导致路径被剥离

**现象**

配置 `proxy_pass http://api:3000/` 时，Nginx 会剥离 location 前缀。请求 `/rest/v1/artworks` 被转成 `/v1/artworks` 发给后端，导致后端路由错位并返回 404。

**处理办法**

调整 Nginx 反代配置，去掉会剥离前缀的错误写法，确保 `/rest/v1/...` 原样进入 Node API。

**沉淀**

修改 Nginx 反代后，必须用真实业务端点验证，而不是只看首页是否 200。至少检查 `/rest/v1/revenue?limit=1` 和本次新增表端点。

### 6. 新增表后 API 白名单遗漏

**现象**

新增 `artworks`、`space_payments`、`expense` 等表后，如果只建表但没有同步 `server.js` 的表映射和字段白名单，POST 会失败，有时表现为 404 或 400，定位不直观。

**处理办法**

形成新增表“三件套”规则：

- 数据库建表或迁移脚本。
- `server.js` table map / 视图映射。
- `server.js` TABLE_COLS / JSONB_COLS / 数值字段白名单。

**沉淀**

新增表、字段、视图不能只改 SQL。必须同时验证：初始化 SQL、生产迁移、后端白名单、前端模型、实际 API 写入。

### 7. 中文请求体乱码

**现象**

部分 API 处理请求体时使用 `body += chunk`，Node Buffer 在字符串拼接时可能按非 UTF-8 方式解码，导致中文字段乱码。

**处理办法**

将相关位置改为：

```js
body += chunk.toString('utf8');
```

**沉淀**

凡是手写 Node HTTP body 解析，都必须显式按 UTF-8 解码。涉及中文项目名、客户名、说明、票据标题的接口，要额外做中文写入和读取验证。

### 8. 上传文件不能挂到只读静态目录

**现象**

画廊作品图片上传时，原计划直接放到 Nginx 静态目录，但容器内对应 rootfs/挂载路径不适合写入，容易出现只读或权限问题。

**处理办法**

- 新增 `uploads-data` Docker volume。
- API 容器负责写入上传文件。
- Nginx 容器以只读方式通过 `/uploads/` alias 托管文件。
- 文件 URL 使用 `/uploads/...` 相对路径。

**沉淀**

静态前端文件和运行时上传文件要分开管理。上传文件必须走独立 volume，并明确 API 写权限、Nginx 读权限、备份策略和清理策略。

### 9. 前端文件上传成功但浏览器仍加载旧版本

**现象**

前端静态文件 scp 到云端后，浏览器可能继续使用缓存。只看 scp 成功不能证明线上用户拿到了新代码。

**处理办法**

- 每次修改 JS/CSS 同步更新 `app/index.html` 中的 cache-bust token。
- 发布后用 curl 拉取首页和具体文件，确认 token、文件大小和关键代码片段。
- 对核心文件检查云端 mtime。

**沉淀**

前端部署验证至少包含三层证据：

- `/opt/aiwei/app/...` 文件 mtime 是当前时间。
- `GET /` 的 HTML 包含新 token。
- `GET /js/xxx.js?v=<新token>` 返回的新文件包含本次改动。

### 10. 云端路径映射容易混淆

**现象**

本地源码在 `app/js/ui.js`，云端宿主机路径是 `/opt/aiwei/app/js/ui.js`，但浏览器 URL 是 `/js/ui.js`。如果误访问 `/app/js/ui.js`，Nginx 可能 fallback 到 `index.html`，返回 200，造成“以为文件存在”的误判。

**处理办法**

明确路径规则：

- scp 目标：`/opt/aiwei/app/js/ui.js`。
- 浏览器访问：`/js/ui.js`。
- 容器内静态 root：`/usr/share/nginx/html/`，没有 `/app/` 这一层。

**沉淀**

验证静态文件时不能只看 HTTP 200，必须看字节数、token 或关键内容。隐藏文件如 `VERSION` 不能用 curl 验证，因为可能 fallback 到首页，必须用 `ssh cat /opt/aiwei/VERSION`。

### 11. `server.js` 修改后只重启容器不生效

**现象**

API 容器镜像是自建镜像。上传新的 `server.js` 后，如果只执行 `docker compose restart api`，容器仍可能使用旧镜像内容，导致代码不生效。

**处理办法**

后端发布固定流程：

```bash
scp server.js root@122.51.56.50:/opt/aiwei/
ssh root@122.51.56.50 "cd /opt/aiwei && docker compose build api && docker compose up -d api"
```

**沉淀**

前端文件是挂载目录，上传即生效；后端文件进入镜像，必须重建 API 容器。两类部署不能混用同一套动作。

### 12. 批量 scp 可能静默漏传

**现象**

一次传多个文件时，曾出现部分文件没有更新 mtime 的情况，后续线上表现和本地代码不一致。

**处理办法**

- 关键发布文件改为单文件 scp。
- 每传一个文件后立刻 `ls -la` 验证 mtime 和大小。
- 发布后再用 HTTP 验证新 token 和关键内容。

**沉淀**

部署不是“命令跑完”就结束，必须逐文件确认落地。尤其是 `index.html`、`ui.js`、`store.js`、`auth.js`、`supabase-config.js` 这类核心文件。

### 13. SSH `Exceeded MaxStartups` 导致连接被重置

**现象**

部署时多次 ssh/scp 返回 `Connection reset`，调试日志出现 `Exceeded MaxStartups`。连续重试会持续占用未认证连接槽，反而加剧失败。

**处理办法**

- 触发后停止连续重试，等待至少 30 秒。
- scp 增加 `ServerAliveInterval`、`ConnectTimeout`。
- 等待期间用 HTTP curl 做只读验证，区分“SSH 限流”和“服务宕机”。

**沉淀**

SSH 抖动不一定是服务器挂了。先用 curl 验证业务入口和 API，如果 HTTP 正常，说明问题主要在 SSH 链路。

### 14. 版本文件 `VERSION` 曾漏传到云端

**现象**

本地 `VERSION` 已升级并提交，但云端 `/opt/aiwei/VERSION` 不存在。运营侧无法读取云端真实版本。

**处理办法**

- 手动 scp `VERSION` 到 `/opt/aiwei/VERSION`。
- 在项目规则中补充：每次升级 `APP_VERSION` 时，同步上传 `VERSION`。
- 路径映射表中明确 `VERSION` 与 `app/` 同级，不在 Nginx 静态目录内。

**沉淀**

版本信息要作为发布对象纳入检查清单。`APP_VERSION`、`LAST_UPDATE`、`index.html` cache-bust token、云端 `VERSION` 必须一起核对。

### 15. HTTPS 域名接入后前端仍写死 HTTP IP

**现象**

系统接入 `https://iwe.ucanart.cc` 后，旧前端配置仍写死 `http://122.51.56.50`。这会带来 mixed content、登录失败和新旧入口不一致风险。

**处理办法**

- 将 `app/js/supabase-config.js` 中 API base 改为浏览器当前 `window.location.origin`。
- 发布 `same-origin-api-20260815` token。
- 验证 `https://iwe.ucanart.cc/rest/v1/revenue?limit=1` 和登录接口能到达后端。

**沉淀**

正式域名上线后，前端应优先同源请求 API。硬编码 IP 只能作为运维诊断入口，不应作为业务入口。

## 四、当前稳定部署规则

### 前端文件

1. 修改 `app/index.html`、`app/js/*.js` 或 `app/css/style.css`。
2. 更新 `index.html` 中相关文件的 cache-bust token。
3. 单文件 scp 到 `/opt/aiwei/app/...`。
4. 验证云端 mtime、首页 token、HTTP 文件大小和关键内容。

### 后端 `server.js`

1. 本地先做 `node --check server.js`。
2. scp 到 `/opt/aiwei/server.js`。
3. 执行 `docker compose build api && docker compose up -d api`。
4. 检查 API 日志和关键端点。

### 数据库迁移

1. 先确认生产表结构和现有数据量。
2. 准备幂等 SQL 或明确回滚方式。
3. 执行前记录影响范围。
4. 执行后核对表结构、记录数、API 读写和前端流程。
5. 同步更新 `app/sql/init.sql`，避免新环境缺字段。

### 发布后最低验证

- 首页返回 200，包含新 cache-bust token。
- 关键 JS/CSS 文件返回 200，大小和内容正确。
- API 容器日志无 `SyntaxError`、`ReferenceError`。
- `/rest/v1/revenue?limit=1` 返回 200。
- 涉及新增表时，新增表 GET/POST/PATCH 至少覆盖一次。
- 涉及业务写入时，用 `test4` 测试账号验证，并清理测试数据。

## 五、仍需关注的风险

| 风险 | 当前状态 | 建议 |
|---|---|---|
| API 鉴权不足 | 早期 API 主要依赖入口不公开和前端角色控制 | 增加服务端 Token/JWT 鉴权中间件 |
| 数据库备份 | 已有备份脚本，但仍需确认生产定时任务和恢复演练 | 每日自动备份 + 定期恢复测试 |
| 服务器无 Swap | 2026-08-15 核实内存约 3.3 GiB，无 Swap | 监控 Docker 内存，必要时增加 Swap 或升级配置 |
| PostgreSQL 端口暴露 | 文档显示 5432 依赖安全组限制 | 复核腾讯云安全组，仅允许必要来源 |
| 手工 scp 部署 | 可控但易漏传 | 后续可引入 GitHub Actions 或脚本化发布清单 |
| 文档与真实云端漂移 | 曾发生 `VERSION` 漏传、路径误判 | 每次部署后把 mtime、token、回滚点写入开发日志 |

## 六、总复盘

这次迁移的正确方向是“轻量自托管”：没有把整个 Supabase 搬到服务器上，而是保留前端形态，重写最小 API 层，把数据落到本地 PostgreSQL。这样既解决了国内访问问题，也控制了服务器资源和月成本。

迁移后的主要问题不在“能不能跑起来”，而在“线上事实是否真的等于本地预期”：路径映射、缓存、Nginx 反代、后端镜像重建、白名单、SSH 限流、版本文件，都曾造成过误判。后来形成的发布纪律是这次迁移最大的资产：

- 任何部署都要验证文件落地、HTTP 内容、API 日志和核心业务流程。
- 前端、后端、数据库三类变更必须使用不同发布动作。
- 新增表字段必须同步 SQL、后端白名单、前端模型和生产迁移。
- 不能把 HTTP 200 当成正确，必须看内容、大小、token 或数据库结果。

后续如果继续扩展系统，优先补 API 鉴权、自动备份、发布自动化和服务器安全组复核。这些不是功能亮点，但会决定系统能否长期稳定承载美术馆日常经营数据。
