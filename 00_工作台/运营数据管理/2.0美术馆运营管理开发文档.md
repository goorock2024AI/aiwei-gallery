## 一、2.0 版本目标

2.0 的目标不是在 1.0 上增加报表，而是将当前“运营数据管理”升级为“美术馆运营管理”：

- 用统一业务模型组织收入、支出、商品、活动、画廊、空间和合作。
- 将 4 个业务层和 3 条能力轴固化到数据结构、业务流程和管理页面中。
- 优先优化数据库结构和代码结构，为后续 3.0“经营管理”与可视化分析打基础。
- 保护 1.0 已有生产数据，任何阶段不得覆盖、破坏或不可逆修改原始经营流水。
- 建立可暂停、可修正、可回滚的开发与上线机制。

2.0 要回答的问题：

| 问题 | 说明 |
|---|---|
| 这笔收入属于哪条业务？ | 到馆参观、现场消费、体验活动、艺术交易与合作 |
| 这笔支出支持哪项业务或能力？ | 业务层成本、内容/IP、观众/会员、商务/合作 |
| 哪些商品、活动、项目、作品正在贡献收入？ | 建立可追踪、可比较、可治理的数据口径 |
| 当前运营数据是否能支撑管理判断？ | 发现数据缺口、归类混乱、成本缺失、流程问题 |
| 后续 3.0 可视化分析需要哪些稳定事实？ | 为经营诊断和集团管理层展示提供数据基础 |

## 二、产品定位

### 1.0 当前定位

**运营数据管理：** 记录收入、支出、日结、产品、画廊、空间等基础经营事实。

核心问题：

- 今天收了多少钱？
- 今天花了多少钱？
- 哪些流水需要日结？
- 产品、作品、空间数据是否被记录？

### 2.0 目标定位

**美术馆运营管理：** 用业务结构统一管理美术馆的日常运营、收入归属、成本归属和业务执行。

核心问题：

- 美术馆的业务是否被正确组织？
- 收入、成本、商品、活动、画廊、空间是否有统一管理口径？
- 哪些业务层稳定，哪些业务层薄弱？
- 哪些能力短板影响业务发展？

### 3.0 后续定位

**经营管理：** 基于 2.0 稳定数据口径，做可视化分析、经营诊断、项目改进和管理层决策展示。

2.0 只做基础运营汇总和管理入口，不提前承担 3.0 的复杂可视化驾驶舱职责。

## 三、业务结构模型 1.0

艾维美术馆定位：

**美术馆 + 艺术空间 + 轻画廊**

### 四个业务层

| 业务层 | 核心作用 | 当前收入形式 | 未来扩展 |
|---|---|---|---|
| 到馆参观 | 获得观众与内容注意力 | 门票、套票 | 导览、特展票、联票 |
| 现场消费 | 提高单客消费贡献 | 文创、饮料、咖啡、展览周边 | 高毛利文创、展览限定、礼品组合 |
| 体验活动 | 把参观变成参与和复购 | 工坊、课程、亲子、团建、沙龙 | 研学、公共教育、企业体验产品 |
| 艺术交易与合作 | 承接高客单收入和外部资源 | 画廊销售、版画、空间租赁、品牌活动 | 艺术家联名、藏家服务、商业合作 |

### 三条能力轴

| 能力轴 | 作用 | 典型数据对象 |
|---|---|---|
| 内容/IP 能力 | 让展览、产品、课程、艺术品都有可传播、可销售、可复用的内容资产 | 展览内容、艺术家资料、作品故事、课程文本、商品故事 |
| 观众/会员能力 | 把一次到访转成复购、社群、活动参与、购买和推荐 | 会员、观众标签、活动参与、复购、触达记录 |
| 商务/合作能力 | 把空间、艺术家、展览和品牌调性转成合作项目与高价值收入 | 合作项目、场地租赁、品牌活动、报价、客户线索 |

### 模型使用原则

- 业务层用于组织收入、支出、商品、活动、画廊和空间。
- 能力轴用于识别支撑能力与短板，不要求每笔流水都强行归入能力轴。
- 内容/IP 不在 2.0 中单独作为第五业务层，而是作为横向能力支撑四个业务层。
- 若未来内容/IP 形成稳定独立收入，可在 3.0 或后续版本升级为独立业务模块。

2.0 一级任务模块确认分为 6 个：

## 六、数据安全原则

2.0 开发必须遵守以下原则：

1. **原始数据不可覆盖**
   - `revenue`、`expense`、`daily_closings`、`gallery_sales`、`creative_products`、`artworks`、`space_usage`、`space_payments` 等 1.0 核心表必须保留。

2. **新增优先**
   - 优先使用新增表、新增字段、新增视图、新增映射关系。
   - 避免删除旧字段或改写旧字段语义。

3. **映射可撤销**
   - 历史归类通过映射表和规则完成。
   - 不把映射结果直接写死到原始流水中。

4. **新旧可对账**
   - 2.0 统计结果必须能追溯到 1.0 原始流水。
   - 每个重要视图需要说明来源表和计算规则。

5. **生产改动必须有备份**
   - 任何数据库迁移、生产部署、权限相关变更前，必须确认备份和回滚点。

## 七、回滚与暂停机制

回滚逻辑采用三档，不把普通问题都视为回滚触发。

| 级别 | 处理方式 | 典型触发条件 |
|---|---|---|
| 观察/修正 | 不回滚，记录问题并修正 | 统计口径偏差、映射不准、商品别名不完整、页面展示问题 |
| 暂停切换 | 保留 2.0 结构，关闭入口或不启用新流程 | 2.0 页面影响判断、录入体验不稳定、部分接口异常、新旧口径暂时无法对账 |
| 正式回滚 | 恢复 1.0 代码或数据库状态 | 1.0 核心功能不可用、原始数据被覆盖/删除/污染、权限/安全异常、生产 API 大面积失败 |

### 不触发正式回滚的情况

- 某个业务类型归类不准。
- 商品别名匹配不完整。
- 某张统计表数字有偏差。
- 2.0 页面样式或交互问题。
- 历史数据映射需要补规则。

### 触发暂停切换的情况

- 2.0 新录入流程让前台无法稳定完成收银。
- 支出归属字段导致日结解释混乱。
- 2.0 统计与 1.0 日结持续无法对账。
- 新增 API 偶发影响响应或性能。

### 触发正式回滚的情况

- 1.0 收银、支出、日结、产品、画廊、空间核心流程不可用。
- 原始收入、支出、日结数据被覆盖、删除或错误改写。
- 出现权限绕过、敏感信息暴露或未授权写入。
- 数据库迁移导致旧表不可用。
- 新代码导致生产 API 大面积失败。

## 八、建议数据结构方向

具体字段在 M2 阶段确认。当前只记录方向，不作为最终迁移脚本。

| 类型 | 建议对象 | 用途 |
|---|---|---|
| 字典表 | `business_layers` | 四大业务层 |
| 字典表 | `business_types` | 门票、文创、饮料、咖啡、工坊、画廊、场地、品牌活动等 |
| 字典表 | `capability_axes` | 内容/IP、观众/会员、商务/合作 |
| 字典表 | `cost_types` | 商品采购、活动成本、展览成本、空间成本、营销成本、内容成本等 |
| 映射表 | `business_mapping_rules` | 旧数据到业务结构的自动归类规则 |
| 映射表 | `product_aliases` | 商品名称清洗与别名合并 |
| 归属表 | `revenue_business_links` | 收入流水与业务层/业务类型关系 |

| 视图 | `business_revenue_facts` | 2.0 收入事实视图 |
| 视图 | `business_cost_facts` | 2.0 成本事实视图 |
| 视图 | `business_profit_facts` | 2.0 毛利事实视图 |

- 1.0 视图 `revenue_facts` 保留。
- 2.0 新建业务事实视图，不直接替换旧视图。
- 历史清洗优先通过别名表和映射表完成。

## 九、2.0 第一批核心指标

2.0 只做基础运营管理指标，复杂分析留给 3.0。

| 指标 | 公式方向 | 作用 |
|---|---|---|
| 业务层收入 | 按业务层汇总收入事实 | 看收入结构 |
| 业务层成本 | 按业务层/能力轴汇总支出或成本 | 看成本结构 |
| 业务层毛利 | 业务层收入 - 可归属成本 | 看经营质量 |
| 每位观众收入 | 总经营收入 / 门票人数 | 看单客贡献 |
| 现场消费/人 | 现场消费收入 / 门票人数 | 看现场转化效率 |
| 文创转化率 | 文创订单数 / 门票人数 | 看文创购买转化 |
| 文创客单价 | 文创销售额 / 文创订单数 | 看商品结构与高客单能力 |
| 咖啡/饮料销量 | 咖啡或饮料销量 | 看停留与即时消费 |
| 工坊收入 | 工坊收入与参与项目 | 看体验活动稳定性 |
| 画廊成交额 | 作品销售收入与成交数 | 看高价值转化 |
| 未归类金额 | 未能映射到业务层的收入/支出 | 看数据治理缺口 |
| 缺成本商品 | 有销售但无成本价的商品 | 看毛利核算缺口 |

| 现场消费 | 观众到馆后，围绕停留、购物、休憩产生的即时消费 | 文创零售、展览周边、饮料、咖啡、书籍、小礼品、现场零售组合 | 工坊课程、画廊作品、空间租赁、品牌活动 |
| 体验活动 | 观众或客户为参与艺术体验、课程、工坊、沙龙、团建内容而产生的收入 | 工坊、课程、亲子活动、研学、团建体验、艺术沙龙报名费 | 单纯门票、单纯零售、单纯场地出租、作品销售 |

边界确认：

- 咖啡套票不作为独立业务层；在当前 1.0 口径下，咖啡套票等同于到馆参观收入，不拆分为咖啡销售收入。
- 企业团建按主要收入实质归类：以体验内容为主归入“体验活动”，以空间和定制合作为主归入“艺术交易与合作”；复杂项目后续允许拆分。
- 空间租赁归入“艺术交易与合作”。
- 内容/IP 不单独作为第五业务层；授权、联名、赞助、品牌合作等收入先归入“艺术交易与合作”，内容/IP 继续作为横向能力轴。

### M1-04 能力轴使用边界确认记录

确认日期：2026-08-30

M1-04 已确认能力轴不是收入分类，而是用于判断“这件事在提升美术馆哪种长期能力”。能力轴用于补充业务层和业务类型，不能替代业务层。

| 能力轴 | 定义 | 主要使用对象 | 不使用场景 |
|---|---|---|---|
| 内容/IP 能力 | 把展览、艺术家、作品、课程、商品转化为可传播、可复用、可销售的内容资产 | 展览内容、艺术家资料、作品故事、课程文本、商品故事、导览内容、联名内容 | 普通门票流水、普通商品销售流水 |
| 观众/会员能力 | 把一次到访转化为复购、社群、活动参与、消费和推荐 | 会员、观众标签、活动参与、私域触达、复购记录、推广活动 | 仅记录金额且无法识别观众关系的普通流水 |
| 商务/合作能力 | 把空间、展览、艺术家、品牌调性转化为合作项目和高价值收入 | 品牌活动、企业合作、场地客户、赞助、联名、画廊客户、合作线索 | 常规散客消费、普通咖啡饮料销售 |

使用规则：

| 对象 | 是否使用能力轴 | 规则 |
|---|---|---|
| 收入流水 | 默认不强制 | 收入先归业务层和业务类型；只有合作、联名、赞助等收入才建议标能力轴 |
| 支出流水 | 建议使用 | 用于判断这笔支出是在支持内容、观众还是商务能力 |
| 项目/活动 | 建议使用 | 一个项目可以关联一个主能力轴，必要时允许多个能力轴 |
| 商品 | 可选使用 | 普通商品不必标；展览限定、艺术家联名、IP 商品可标内容/IP |
| 改进任务 | 建议使用 | 用于判断系统或运营改进到底补哪类能力短板 |
| 历史数据 | 不强制补齐 | 无法判断的历史记录保留为空或待确认 |

边界确认：

- 能力轴不进入每一笔普通收入流水的必填项。
- 能力轴更适合作为支出、项目、商品、合作和改进任务的能力归因字段。
- 能力轴可用于 3.0 经营诊断，但 2.0 阶段只建立基础口径和归属能力。

- 文创与饮料必须拆开；拆不开的历史数据不强行归类。
- 场地旧口径、其他收入、赞助、活动服务等保留人工确认空间。

### M1-07 2.0 指标口径确认记录

确认日期：2026-08-30

M1-07 已确认 2.0 第一批基础运营指标。该指标口径用于支持 2.0 的业务管理和 3.0 的经营分析准备，但本阶段不引入复杂评分、健康度模型或预测模型。

| 指标 | 计算口径 | 主要用途 |
|---|---|---|
| 业务层收入 | 按 2.0 业务层汇总收入 | 判断收入结构 |
| 业务层成本 | 按支出映射汇总可归属成本 | 判断成本结构 |
| 业务层毛利 | 业务层收入 - 可归属成本 | 判断业务质量 |
| 到馆参观人数 | 普通门票数量 + 咖啡套票数量 | 判断真实到馆规模 |
| 门票收入 | 普通门票收入 + 咖啡套票收入 | 判断参观收入 |
| 现场消费收入 | 文创零售 + 饮料零售 + 独立咖啡销售 | 判断单客消费贡献 |
| 现场消费/人 | 现场消费收入 / 到馆参观人数 | 判断现场转化效率 |
| 文创客单价 | 文创销售额 / 文创订单数 | 判断文创商品结构 |
| 文创转化率 | 文创订单数 / 到馆参观人数 | 判断参观到购买转化 |
| 饮料销量与毛利 | 饮料销售数量、销售额、毛利 | 判断即时消费贡献 |
| 咖啡销量与收入 | 独立咖啡销量、独立咖啡收入 | 判断咖啡单独经营表现 |
| 工坊收入 | 工坊/体验收入 | 判断体验活动能力 |
| 画廊成交额 | 画廊销售收入 | 判断艺术交易表现 |
| 空间合作收入 | 空间租赁 + 品牌活动/企业合作收入 | 判断商务合作能力 |
| 未归类收入/支出 | 待归类金额 | 判断数据治理缺口 |
| 缺成本商品 | 有销售但无成本价的商品 | 判断毛利核算缺口 |

边界确认：

- 到馆参观人数 = 普通门票数量 + 咖啡套票数量。
- 独立咖啡销售不计入到馆参观，只计入现场消费。
- 咖啡套票在当前 1.0 口径下等同于到馆参观收入，不拆分为独立咖啡收入。
- 文创、饮料、咖啡需要在现场消费中分开统计，避免混淆转化率和客单价。
- 2.0 只确认基础指标和异常识别口径，不做经营健康度评分和复杂预测。

- 独立咖啡边界必须保留：7 月有 66 条咖啡销售记录且均为咖啡独立记录；8 月有 76 条咖啡销售记录，其中 68 条为仅咖啡记录。独立咖啡不应计入到馆参观。
- 工坊口径可用：7 月 33 条、3280.00 元；8 月 18 条、1432.00 元，金额与明细可对回。
- 零售金额可对回：7、8 月 `retail_items` 明细合计与 `retail_amount` 无实质差异。
- 画廊口径可用但档案关联不足：7 月 6 笔画廊销售，成交额 4180.00 元，佣金 0.00 元，净额 4180.00 元；其中 4 笔缺作品编号。8 月无画廊销售记录。
- 空间合作口径可用但类型需细化：7 月空间收款 5580.00 元，含企业团建、场地租赁、展览；8 月空间收款 4660.00 元，含场地租赁、展览。
- 支出口径部分可用：8 月支出已使用标准分类；7 月存在“材料、运费、其他”等历史非标分类，共 12 条、1667.34 元，需要兼容映射。

发现的问题清单：

| 问题 | 影响 | 建议进入模块 |
|---|---|---|
| 商品标准名匹配不足 | 文创、饮料毛利和单品排名不能稳定依赖商品名精确匹配 | M2 商品主数据 / M4 商品别名治理 |

M1-08 判断：

现有 4 个业务层、业务类型字典、收入/支出映射规则和第一批指标口径基本可解释 7、8 月主要经营数据。问题主要集中在数据治理和主数据结构，不构成业务模型失败。M1-08 可以进入馆长确认；确认后进入 M1-09 评审与冻结。

- 当前 1.0 数据如何解释为 2.0 业务语言。
- 哪些问题属于业务模型，哪些问题属于数据结构和历史治理。

M1 的主要成果：

- 提高门票销量、提高客单价、优化文创呈现、发展工坊和画廊，不能只用单一指标判断；必须回到业务层和能力轴共同判断。
- 咖啡销售不等于到馆参观，咖啡套票等于到馆参观；这是后续所有到馆、转化、现场消费指标的基础边界。

- 画廊不是传统美术馆的标准收入核心，但符合艾维“美术馆 + 艺术空间 + 轻画廊”的定位，因此应作为正式业务组成部分。
- 内容/IP 不作为单独一级收入大类，而是作为能力轴贯穿展览、商品、课程、画廊和合作。
- 数据治理问题不能反向推翻业务模型；商品混名、成本缺失、历史分类不统一，应进入 M2/M4 解决。

对 M2 的约束：

- M2 不能直接重写 1.0 原始流水；必须优先通过新增表、字段、视图、映射表解释历史数据。
- M2 的数据库设计必须先服务业务口径稳定，再考虑前端呈现。
- M2 必须把商品主数据和商品别名作为核心设计对象，否则文创、饮料、成本、毛利、客单价都会继续不稳定。
- M2 必须保留“待归类”机制，不能为了报表好看强行归类。
- M2 的迁移方案必须包含备份、回滚、只读校验、灰度切换和不破坏 1.0 使用的兼容策略。
- M2 不应提前做 3.0 的经营大屏、复杂评分和预测模型。

是否可以进入 M2：

可以进入，但应带条件进入。条件不是继续讨论业务模型，而是在 M2 开始时先完成数据库结构与迁移安全方案，特别是商品主数据、业务映射视图、支出映射、画廊作品关联和回滚机制。

M1 最终评价：

M1 是有效的。它没有停留在“做几个收入分类”的层面，而是把艾维美术馆的业务定位、经营结构、数据解释方式和未来系统建设方向连在了一起。M1 已经能够指导 M2 开发，但 M1 不应替代 M2 的数据结构设计，也不应替代 M4 的历史数据治理。

### M2-03 商品主数据与别名设计草案

执行日期：2026-09-01

设计目标：

- 建立文创、饮料及其他零售商品的统一主数据口径。
- 解决历史流水中的同品异名、不同包装、不同单价、成本价匹配和饮料排除问题。
- 支撑 2.0 的文创客单价、文创转化率、饮料销量、商品毛利、利润贡献排名和库存治理。
- 继续保护 1.0 原始 `revenue.retail_items`，不直接改写历史流水。

#### 1. 现状依据

| 事项 | 当前事实 | 对设计的影响 |
|---|---|---|
| 商品主数据 | 线上 `creative_products` 共 124 条；124 条有零售价，121 条有成本价，52 条当前库存大于 0 | 已具备主数据基础，优先复用，不急于新建 `products` 总表 |
| 历史零售明细 | 7-8 月 `retail_items` 主要使用 `product_name/unit_price/qty/amount`，少量使用 `productName/unitPrice` | v2 视图必须兼容多种 JSON 键名 |
| 精确匹配情况 | 按销售名称直接匹配 `creative_products.name`，仍有大量销售名称无法精确匹配 | 必须建立别名表，不能依赖名称完全一致 |
| 饮料混名 | 已见 `水/纯悦水`、`苏打水/纯悦苏打水`、`可乐/可口可乐/可乐听`，且可乐、雪碧、芬达存在 3.5 元与 4 元不同包装 | 别名必须同时考虑标准商品和包装规格/单价 |
| 误判风险 | `水晶冰箱贴`、`永乐大典水壶` 等名称含“水”但不是饮料 | 不能只靠关键词判断饮料，必须有人工确认的 `is_beverage` |
| 成本价基础 | `creative_products.cost_price` 已存在 | 利润贡献排名应优先用主数据成本价，缺成本时进入治理清单 |

以上抽样只用于判断治理压力和字段设计，不作为最终经营统计口径。

#### 2. 商品主数据策略

M2-03 建议继续以 `creative_products` 作为 2.0 商品主数据基础，而不是立即新建一张更大的 `products` 表。

理由：

- 当前文创、饮料和轻零售商品已经集中在 `creative_products`。
- 该表已有成本价、零售价、库存、供应商、SKU、上下架审批字段。
- 立即新建总商品表会带来一次主数据迁移，风险大于收益。
- 2.0 现阶段的核心问题不是“没有商品表”，而是“商品名称、业务类型、包装规格和别名没有统一治理”。

#### 3. `creative_products` 建议扩展字段

| 字段 | 类型建议 | 用途 |
|---|---|---|
| `standard_name` | TEXT | 标准商品名，用于展示和统计；为空时默认等于 `name` |
| `business_type_code` | TEXT | 关联 M1 业务类型，如 `creative_retail`、`beverage_retail` |
| `package_spec` | TEXT | 包装规格，如瓶装、听装、盒、个、套 |
| `barcode` | TEXT | 条码或外部识别码，后续支持扫码和采购入库 |
| `is_beverage` | BOOLEAN | 是否饮料，用于稳定排除饮料和统计饮料 |
| `is_countable_stock` | BOOLEAN | 是否需要库存扣减，区分实物商品、服务、体验类项目 |
| `is_active` | BOOLEAN | 是否仍在使用，避免删除历史商品 |

字段设计原则：

- `name` 保留为当前录入名称，不承担唯一业务口径。
- `standard_name` 用于统计归并，但不要求立刻补齐全部历史数据。
- `business_type_code` 承接 M1 业务类型，优先区分文创零售和饮料零售。
- `is_beverage` 是人工确认字段，不由单价或关键词自动决定。

#### 4. `product_aliases` 建议字段

| 字段 | 类型建议 | 用途 |
|---|---|---|
| `id` | TEXT PRIMARY KEY | 别名记录 ID |
| `alias_name` | TEXT | 历史流水或前台录入中出现的商品名称 |
| `standard_product_id` | TEXT | 指向 `creative_products.id`，允许为空等待确认 |
| `standard_name` | TEXT | 归并后的标准商品名，便于缺商品 ID 时先治理 |
| `business_type_code` | TEXT | 文创零售、饮料零售等业务类型 |
| `package_spec` | TEXT | 包装规格，例如听装、瓶装 |
| `unit_price` | NUMERIC | 匹配该别名时的销售单价，解决同名不同规格 |
| `cost_price_snapshot` | NUMERIC | 可选成本快照，用于历史利润复算和成本变动留痕 |
| `is_beverage` | BOOLEAN | 是否饮料 |
| `match_priority` | INTEGER | 多条规则命中时的优先级 |
| `confidence` | TEXT | `confirmed`、`suggested`、`pending` |
| `is_active` | BOOLEAN | 是否启用 |
| `notes` | TEXT | 说明人工判断依据 |

推荐唯一性规则：

- 同一 `alias_name + unit_price + package_spec` 只能对应一个启用别名。
- 允许同一个标准商品拥有多个别名。
- 允许同一个别名在不同 `unit_price/package_spec` 下对应不同包装。

#### 5. 饮料别名治理规则

| 历史名称/情况 | 建议标准口径 | 包装与单价规则 |
|---|---|---|
| `水`、`纯悦水` | 纯悦水 | 单价 2 元，饮料零售 |
| `苏打水`、`纯悦苏打水` | 纯悦苏打水 | 单价 5 元优先按瓶装；历史 4 元单独保留规格或标待确认 |
| `可乐`、`可口可乐` | 可口可乐 | 单价 3.5 元为听装，单价 4 元为瓶装 |
| `雪碧` | 雪碧 | 单价 3.5 元为听装，单价 4 元为瓶装 |
| `芬达` | 芬达 | 单价 3.5 元为听装，单价 4 元为瓶装 |
| `果粒橙`、`美汁源` | 果粒橙/美汁源 | 若实际为同一产品，需馆长确认后合并；否则保留两个标准品 |
| `拿铁咖啡`、`costa咖啡`、`咖世家咖啡` | 咖啡饮品或饮料零售待确认 | 若属于瓶装/罐装成品饮料，归饮料零售；若属于现制咖啡，不并入零售饮料 |

治理注意：

- 单价低于 8 元只能作为“待排查提示”，不能作为饮料判断依据。
- 产品名称明显是饮料可作为初筛，但最终以 `product_aliases.is_beverage` 为准。
- 名称含饮料关键词但实际不是饮料的商品，需要显式标为非饮料，例如 `水晶冰箱贴`、`永乐大典水壶`。

#### 6. 利润贡献计算规则

| 场景 | 成本来源优先级 | 计算方式 |
|---|---|---|
| 销售明细能匹配商品主数据 | `creative_products.cost_price` | `销售额 - 成本价 * 销量` |
| 销售明细匹配别名且有成本快照 | `product_aliases.cost_price_snapshot` | `销售额 - 成本快照 * 销量` |
| 商品成本价缺失 | 标记为缺成本 | 不进入确定利润排名，进入待补成本清单 |
| 同名不同单价 | 先按 `alias_name + unit_price + package_spec` 匹配 | 分包装计算利润，不合并成本 |
| 历史成本变动 | 优先保留成交时成本快照 | 避免后续改成本价影响历史利润 |

M2-03 建议在别名表中预留 `cost_price_snapshot`，但不要求第一次迁移就补齐所有快照。后续如果要严格核算历史毛利，可再设计商品成本变更记录。

#### 7. 与 2.0 事实视图的关系

`business_revenue_facts_v2` 处理零售时，应按以下顺序解释商品：

1. 从 `revenue.retail_items` 展开销售行。
2. 兼容读取 `product_name/productName/name`、`unit_price/unitPrice/price`、`qty/quantity`、`amount`。
3. 优先匹配 `product_aliases` 的 `alias_name + unit_price`。
4. 匹配不到别名时，再尝试匹配 `creative_products.name` 或 `creative_products.standard_name`。
5. 仍无法匹配时，进入 `待归类收入` 或 `缺商品主数据` 标记。
6. 根据 `is_beverage` 和 `business_type_code` 输出文创零售或饮料零售。

#### 8. 前台管理建议

| 页面/功能 | 2.0 建议 |
|---|---|
| 产品管理 | 在现有文创/零售管理中增加业务类型、标准名、包装规格、是否饮料、是否计库存 |
| 别名管理 | 新增轻量管理入口，展示“历史名称、单价、建议标准品、确认状态” |
| POS 选择商品 | 优先显示标准商品名和规格，避免继续产生混乱名称 |
| 销售分析 | 文创统计默认排除 `is_beverage=true`；饮料统计单独展示 |
| 成本补全 | 对缺成本商品给出清单，不阻止销售录入 |

#### 9. 待确认点

| 编号 | 待确认问题 | 建议默认 |
|---|---|---|
| M2-03-D1 | 是否确认 `creative_products` 继续作为 2.0 商品主数据基础 | 确认复用，先不新建 `products` 总表 |
| M2-03-D2 | 是否确认饮料判断以 `is_beverage` 为最终口径，而不是单价低于 8 元 | 确认，低价只作为提示 |
| M2-03-D3 | 可乐、雪碧、芬达是否按 3.5 元听装、4 元瓶装拆规格 | 确认按单价拆包装规格 |

M2-03 草案结论：

- 商品主数据不宜重建，优先扩展 `creative_products` 并新增 `product_aliases`。
- 饮料与文创的分离，应从“临时筛选规则”升级为“商品主数据 + 别名表 + 人工确认字段”。

### M2-04 收入事实视图 2.0 设计草案

执行日期：2026-09-01

设计目标：

- 在现有 `revenue_facts` 基础上，新增只读视图 `business_revenue_facts_v2`。
- 将收入事实统一输出为可分析的业务层、业务类型、商品、数量、金额、治理状态。
- 支持门票、咖啡套票、咖啡、工坊、文创、饮料、画廊、空间和品牌活动的统一统计。
- 为 2.0 经营分析页面和 3.0 可视化系统提供稳定收入事实口径。

#### 1. 与现有 `revenue_facts` 的关系

| 项目 | `revenue_facts` 当前口径 | `business_revenue_facts_v2` 建议口径 |
|---|---|---|
| 定位 | 1.0 统一收入事实视图 | 2.0 业务结构收入事实视图 |
| 数据粒度 | 多数收入按原记录聚合；零售整体为一行 `文创` | 零售、工坊等尽量展开到商品/项目行；非明细收入保留汇总行 |
| 业务分类 | `category` 只有 1.0 类别 | 增加 `business_layer_code/name`、`business_type_code/name` |
| 商品治理 | 不识别商品别名、包装、饮料 | 关联 `product_aliases`、`creative_products`，输出标准商品和治理状态 |
| 替换策略 | 保留 | 新增 v2 视图，不直接替换旧视图 |

#### 2. 建议输出字段

| 字段 | 含义 |
|---|---|
| `fact_id` | 事实行唯一 ID，建议由来源表、来源记录、来源类型和行序号组合 |
| `source_table` | 来源表，如 `revenue`、`gallery_sales`、`space_payments`、`transaction_adjustments` |
| `source_id` | 来源记录 ID |
| `source_line_key` | JSON 明细行序号或业务分项 key，例如 `retail:3`、`ticket`、`gallery` |
| `business_date` | 业务日期；空间收入按 `space_payments.payment_date` |
| `source_category` | 1.0 原始类别，如门票、咖啡套票、零售、画廊、场地 |
| `business_layer_code` / `business_layer_name` | M1 冻结业务层 |
| `business_type_code` / `business_type_name` | M1 冻结业务类型 |
| `product_id` | 匹配到的 `creative_products.id` 或作品/项目 ID |
| `product_name_raw` | 原始销售名称 |
| `product_name_standard` | 标准商品名或标准项目名 |
| `package_spec` | 包装规格 |
| `unit_price` | 单价 |
| `quantity` | 数量；无数量时默认为 1 或空值，需标治理状态 |
| `gross_amount` | 原始销售额 |
| `net_amount` | 净收入；画廊扣佣金，退款/调整按负数行处理 |
| `payment_method` | 收款方式 |
| `project_name` | 项目/展览/空间项目名称 |
| `handler` | 经手人 |
| `is_beverage` | 是否饮料 |
| `is_manual_override` | 是否人工归属覆盖 |
| `mapping_status` | `confirmed`、`mapped_by_rule`、`matched_by_alias`、`matched_by_product`、`unmatched`、`pending_review` |
| `quality_flags` | JSONB，记录缺商品、缺数量、金额不一致、待归类等治理标记 |
| `created_at` | 原始记录创建时间 |

#### 3. 来源与生成规则

| 来源 | 生成规则 | 默认业务归属 |
|---|---|---|
| `revenue.ticket_amount` | 一条收入记录生成一条门票事实行，数量取 `ticket_qty` | 到馆参观 / 门票/参观票 |
| `revenue.combo_amount` | 一条收入记录生成一条咖啡套票事实行，数量取 `combo_qty` | 到馆参观 / 咖啡套票/参观套票 |
| `revenue.coffee_amount` | 一条收入记录生成一条独立咖啡事实行，数量取 `coffee_qty` | 现场消费 / 咖啡 |
| `revenue.workshop_items` | 优先按 JSON 明细展开；缺明细时按 `workshop_amount` 生成汇总行 | 体验活动 / 工坊/体验 |
| `revenue.retail_items` | 必须按 JSON 明细展开，并兼容 `product_name/productName/name`、`unit_price/unitPrice/price`、`qty/quantity`、`amount` | 通过商品别名或主数据判断文创零售/饮料零售 |
| `revenue.creative_amount` | 作为历史兼容汇总行，不与 `retail_items` 重复计入 | 现场消费 / 文创零售，标记为历史兼容 |
| `revenue.venue_amount` | 作为旧口径收入兼容行 | 艺术交易与合作 / 待归类收入或空间租赁，标记为场地旧口径 |
| `revenue.other_amount` | 根据 `other_desc` 和映射规则判断；无法判断进入待归类收入 | 待归类收入 |
| `gallery_sales` | 每条销售生成一条画廊事实行，金额取成交价，净额取成交价减佣金 | 艺术交易与合作 / 画廊销售 |
| `space_payments` + `space_usage` | 每笔到款生成一条空间事实行，日期取到款日期 | 艺术交易与合作 / 空间租赁或品牌活动/企业合作 |
| `transaction_adjustments` | 退款/部分退款生成负向事实行，跟随原单业务归属；无法跟随则标待归类调整 | 跟随原收入 |

#### 4. 去重与金额校验

| 场景 | 规则 |
|---|---|
| `retail_items` 与 `retail_amount` | 以明细行展开为准；`retail_amount` 只用于校验，不另生成汇总事实行 |
| `workshop_items` 与 `workshop_amount` | 有明细时按明细展开；无明细但有金额时生成汇总行 |
| `creative_amount` 与 `retail_items` | 若同一记录已有 `retail_items` 金额，`creative_amount` 仅在非零且未被明细覆盖时生成兼容行 |
| 退款/部分退款 | 作为负向事实行，不直接改原收入事实 |
| 已作废记录 | 默认排除；如后续要审计作废，可单独做审计视图，不进入经营收入 |
| 金额不一致 | 当明细合计与表头金额差异超过 0.01，输出 `quality_flags.amount_mismatch=true` |

#### 5. 商品匹配优先级

`retail_items` 展开后，商品匹配顺序为：

1. 人工归属表 `record_business_links`，精确到 `source_table + source_id + source_line_key`。
2. 别名表 `product_aliases`，优先匹配 `alias_name + unit_price + package_spec`。
3. 商品主数据 `creative_products`，匹配 `name` 或 `standard_name`。
4. 映射规则 `business_mapping_rules`，按关键词、字段、来源类别兜底。
5. 无法匹配则输出 `mapping_status='unmatched'`，业务类型进入待归类收入。

这个顺序确保人工确认可以覆盖自动规则，也避免“水晶冰箱贴”被关键词误判成饮料。

#### 6. 关键指标支持

| 指标 | v2 视图支持方式 |
|---|---|
| 到馆参观人数 | `business_type_code in ('ticket','visit_combo')` 的数量合计 |
| 门票收入 | 门票/咖啡套票对应事实行金额合计 |
| 文创收入 | `business_type_code='creative_retail'` 且 `is_beverage=false` |
| 文创客单价 | 文创零售金额 / 文创成交订单数；订单数按 `source_id` 去重 |
| 文创转化率 | 有文创事实行的 `source_id` 去重 / 到馆参观人数 |
| 饮料销量 | `is_beverage=true` 的数量合计，可按标准商品和包装拆分 |
| 咖啡收入 | 独立咖啡事实行合计，不把咖啡套票误算为独立咖啡销售 |
| 画廊成交额 | 画廊销售事实行成交价合计 |
| 空间收入 | 空间到款事实行按 `payment_date` 合计 |
| 待归类收入 | `mapping_status in ('unmatched','pending_review')` 或业务类型为待归类收入 |

#### 7. 权限与接口建议

| 项目 | 建议 |
|---|---|
| 视图读写 | `business_revenue_facts_v2` 必须加入 `READ_ONLY_TABLES` |
| API 映射 | 加入 `server.js tableMap`，只开放 GET |
| 角色权限 | admin/editor/viewer 均可读；任何角色都不可写 |
| 前端使用 | 2.0 数据统计和经营分析页面优先读取 v2 视图，1.0 页面可继续读取旧表/旧视图 |
| 敏感信息 | 不输出买家个人敏感信息；画廊销售买方姓名不进入 v2 默认字段 |

#### 8. 待确认点

| 编号 | 待确认问题 | 建议默认 |

### M2-05 支出映射与成本口径设计草案

执行日期：2026-09-01

设计目标：

- 将 1.0 的支出记录升级为可服务经营分析的成本事实口径。
- 支持按业务层、业务类型、成本类型和能力轴分析成本投入。
- 区分“期间支出/现金支出”和“销售成本/已售成本”，避免毛利重复扣减。
- 兼容历史支出分类不统一问题，不直接修改原始 `expense.category`。
- 为 `business_cost_facts_v2` 和后续 `business_profit_facts_v2` 提供稳定输入。

#### 1. 核心原则

M2-05 最重要的设计原则是：成本事实不等于支出流水。

| 概念 | 含义 | 主要来源 | 用途 |
|---|---|---|---|
| 期间支出 | 某一期间实际发生或录入的支出 | `expense` | 看现金消耗、费用结构、报销和经营净收支 |
| 销售成本 | 已售商品、作品或项目对应的成本 | 商品成本、作品结算价、活动直接成本 | 看毛利、利润贡献和产品结构 |
| 能力投入 | 支持内容、观众、商务能力建设的投入 | `expense` 映射 | 看能力短板和资源配置 |
| 待归类成本 | 暂时无法判断业务归属的成本 | 映射失败记录 | 数据治理清单 |

因此，2.0 至少需要同时提供两个成本视角：

| 视角 | 计算方式 | 适合回答的问题 |
|---|---|---|
| 业务毛利视角 | 收入 - 对应销售成本/直接成本 | 哪些商品、活动、画廊项目真正贡献利润 |
| 经营收支视角 | 收入 - 期间支出 | 当月现金经营结果是否健康 |

商品采购类支出可以进入经营收支视角，但在文创、饮料单品毛利中不应再次扣减。单品毛利应优先使用商品主数据或别名映射中的单位成本。

#### 2. 与现有表的关系

| 现有数据 | 当前作用 | M2-05 建议处理 |
|---|---|---|
| `expense` | 记录运营支出，含旧分类 `材料`、`运费`、`其他` 和新分类 `商品采购` 等 | 保留原表，新增映射规则，不覆盖历史分类 |
| `expense_attachments` | 支出发票和支付凭证 | 作为审计与凭证材料，不进入成本事实金额计算 |
| `expense_reimbursements` | 报销凭证包 | 用于报销状态和现金流程，不生成业务成本事实 |
| `creative_products.cost_price` | 文创/饮料产品成本价 | 作为销售成本默认来源 |
| `product_aliases.cost_price_snapshot` | 商品别名和包装成本快照 | 优先用于历史销售成本还原 |
| `artworks.settlement_price` | 作品结算价 | 作为画廊销售成本来源 |
| `gallery_sales.commission` | 画廊佣金 | 默认从收入视图净收入中扣除，不再作为成本重复扣减 |
| `cash_movements` | 现金流动作 | 只做日结和资金核对，不默认生成业务成本 |

#### 4. 成本生成规则

| 来源 | 生成规则 | 默认归属 |
|---|---|---|
| `expense` | 每条支出生成一条期间支出事实行，按 `category`、`project`、`description`、`related_activity` 进行映射 | 映射到成本类型、业务层和能力轴 |
| 文创销售明细 | 从 `business_revenue_facts_v2` 取文创收入行，按商品成本价生成已售成本 | 现场消费 / 文创零售 / 商品进货成本 |
| 饮料销售明细 | 从 `business_revenue_facts_v2` 取饮料收入行，按别名和包装成本生成已售成本 | 现场消费 / 饮料零售 / 商品进货成本 |
| 工坊/体验收入 | 优先匹配活动直接支出；无法匹配时暂不估算成本 | 体验活动 / 工坊或课程 / 活动执行成本 |
| 画廊销售 | 通过 `artwork_no` 或后续作品关联字段匹配 `artworks.settlement_price`，生成作品结算成本 | 艺术交易与合作 / 画廊销售 / 画廊交易成本 |
| 空间租赁/品牌活动 | 不从收入自动生成成本，依赖 `expense` 中项目或人工归属 | 艺术交易与合作 / 空间租赁或品牌活动 |
| 共享运营支出 | 先保留为期间支出和能力投入，不在 M2 默认分摊 | 空间运营、行政财务、人员劳务等 |

#### 5. 支出映射规则

支出映射应复用 M2-02 的 `business_mapping_rules` 和 `record_business_links`，不为支出单独发明一套孤立规则。

映射优先级：

1. 人工归属 `record_business_links`，精确到 `expense.id`。
2. 项目字段 `expense.project` 和 `related_activity`。
3. 支出类别 `expense.category`。
4. 描述关键词 `expense.description`。
5. 无法判断时进入待归类成本。

建议第一批默认映射：

| 原始分类或关键词 | 成本类型 | 业务层 | 能力轴 | 备注 |
|---|---|---|---|---|
| `商品采购`、饮料进货、文创进货 | 商品进货成本 | 现场消费 | 可为空 | 经营收支视角使用；单品毛利用已售成本 |
| `材料`、工坊材料、活动材料 | 活动执行成本 | 体验活动 | 内容/IP 能力 | 需结合项目字段判断 |
| `运费` | 商品进货成本或活动执行成本 | 跟随关联项目 | 可为空 | 无关联时待归类 |
| `物料耗材` | 空间运营成本或活动执行成本 | 跟随项目 | 可为空 | 需人工确认比例较高 |
| `活动展览成本` | 展览与内容成本 | 到馆参观或体验活动 | 内容/IP 能力 | 需结合项目/展览名称 |
| `设备资产` | 设备资产成本 | 待归属或共享运营 | 可为空 | 默认不分摊到单项业务 |
| 行政、财务、办公 | 行政财务成本 | 共享运营 | 可为空 | 后续可做经营净收支 |
| 人员、劳务、兼职 | 人员与劳务成本 | 跟随项目或共享运营 | 可为空 | 需要更细支出录入口径支持 |
| 推广、广告、拍摄、达人 | 市场推广成本 | 跟随项目 | 观众/会员能力 | 可用于判断获客投入 |
| 画框、装裱、作品运输、艺术家结算 | 画廊交易成本 | 艺术交易与合作 | 商务/合作能力 | 与作品销售关联后进入画廊毛利 |

#### 6. 防重复扣减规则

| 场景 | 规则 |
|---|---|
| 商品采购支出 + 文创/饮料销售成本 | 毛利计算只扣销售成本，不再扣当期商品采购支出 |
| 画廊净收入 + 佣金 | 若收入视图已用成交价减佣金得到 `net_amount`，利润视图不再把佣金作为成本扣一次 |
| 工坊收入 + 活动材料支出 | 只有明确关联到该工坊或项目的支出才进入项目毛利 |
| 空间收入 + 空间运营成本 | M2 不自动按比例分摊共享成本，先保留为经营收支视角 |
| 报销记录 + 原支出 | 报销只是资金流程，不生成第二条成本 |
| 日结汇总 + 原始支出 | 日结只核对，不参与成本事实汇总 |

#### 7. 对关键分析的支持

| 分析问题 | 支持方式 |
|---|---|
| 文创零售毛利 | 文创收入事实行 - `sold_cogs` |
| 饮料利润贡献 | 饮料收入事实行 - 按标准商品和包装匹配的 `sold_cogs` |
| 画廊利润贡献 | 画廊净收入 - 作品结算成本 |
| 工坊项目毛利 | 工坊收入 - 直接关联活动执行成本 |
| 业务层成本结构 | `period_expense` 按业务层和成本类型汇总 |
| 能力投入结构 | `expense` 映射到内容/IP、观众/会员、商务/合作能力 |
| 数据治理缺口 | `mapping_status` 为 `unmatched` 或 `pending_review` 的成本金额和数量 |

#### 8. 权限与接口建议

| 项目 | 建议 |
|---|---|
| 视图读写 | `business_cost_facts_v2` 必须加入 `READ_ONLY_TABLES` |
| API 映射 | 加入 `server.js tableMap`，只开放 GET |
| 原始支出 | `expense` 继续作为唯一支出录入表，不被 v2 视图替代 |
| 成本调整 | 人工修正通过映射表和归属表完成，不直接改历史支出原文 |
| 数据质量 | 缺成本、缺归属、疑似重复扣减必须输出治理标记 |

#### 9. 待确认点

| 编号 | 待确认问题 | 建议默认 |
|---|---|---|
| M2-05-D1 | 是否明确区分“期间支出”和“销售成本” | 确认区分，这是避免毛利失真的基础 |
| M2-05-D2 | 文创和饮料毛利是否优先按商品/别名成本价计算，而不是直接按进货支出扣减 | 确认按单位成本计算 |
| M2-05-D3 | `商品采购` 支出是否仍进入经营收支视角，但不进入单品毛利重复扣减 | 确认 |
| M2-05-D4 | 共享运营成本是否暂不自动分摊到业务层毛利 | 确认，M2 先不做强行分摊 |
| M2-05-D5 | 画廊佣金是否默认在收入净额中处理，成本侧不重复扣减 | 确认 |
| M2-05-D6 | 历史 `expense.category` 是否只映射、不覆盖修改 | 确认 |

M2-05 草案结论：

- 2.0 成本设计必须同时支持经营收支和业务毛利，但两者不能混用。
- `business_cost_facts_v2` 应以只读视图形式建立，统一输出期间支出、已售成本、画廊结算成本和项目直接成本。
- 文创、饮料的利润贡献应以销售明细和商品成本为基础，不用当期采购支出直接推算单品毛利。
- 历史支出分类混乱通过映射规则治理，不直接改原始支出记录。
- M2-05 确认后，下一步进入 M2-06，设计画廊与空间关联结构。

### M2-06 画廊与空间关联结构设计草案

执行日期：2026-09-01

设计目标：

- 让画廊销售稳定关联作品档案，支持成交、结算价、佣金、库存和利润贡献分析。
- 让空间收入稳定区分空间租赁、品牌活动、企业合作和内部项目使用。
- 保留 1.0 已有录入习惯和历史文本信息，不用强制清洗覆盖历史记录。
- 为 `business_revenue_facts_v2`、`business_cost_facts_v2` 和后续经营诊断提供可靠关联字段。
- 控制新增结构数量，优先在现有表上补关键字段，避免把 2.0 做得过重。

#### 1. 当前结构判断

| 模块 | 1.0 已有基础 | 当前问题 | M2-06 设计方向 |
|---|---|---|---|
| 画廊作品 | `artworks` 已有作品编号、图片、结算价、零售价、库存数量 | 销售记录主要靠 `artwork_no` 文本匹配，缺少稳定 `artwork_id` | 增加作品 ID 关联，同时保留销售时快照 |
| 画廊销售 | `gallery_sales` 已有成交价、佣金、买方、状态、销售数量 | 成本和作品库存依赖弱匹配；作品档案变化后历史成本可能失真 | 销售时记录结算价快照和净收入快照 |
| 空间使用 | `space_usage` 已有空间、项目、类型、客户、状态、应收 | `type` 是运营场景，不等于 2.0 业务类型 | 增加 2.0 业务类型和合作方式字段 |
| 空间付款 | `space_payments` 已拆子表，按付款日期入账 | 到款能统计，但难判断属于空间租赁还是品牌活动 | 跟随 `space_usage` 的业务归属进入收入事实 |

#### 2. 画廊关联设计

画廊销售应从“文本记录一笔销售”升级为“作品档案 + 成交快照 + 销售事实”的结构。

建议在 `gallery_sales` 增加字段：

| 字段 | 类型建议 | 含义 | 兼容策略 |
|---|---|---|---|
| `artwork_id` | TEXT，可空 | 关联 `artworks.id` | 历史记录先为空，可通过 `artwork_no` 回填 |
| `settlement_price_snapshot` | NUMERIC(12,2) | 销售发生时的作品结算价 | 默认取 `artworks.settlement_price` |
| `retail_price_snapshot` | NUMERIC(12,2) | 销售发生时的标价 | 默认取 `artworks.retail_price` |
| `gross_amount_snapshot` | NUMERIC(12,2) | 成交总额快照 | 默认等于 `price` |
| `net_amount_snapshot` | NUMERIC(12,2) | 净收入快照 | 默认 `price - commission - refund_amount` |
| `gallery_channel` | TEXT | 销售渠道，如馆内、线上、合作方 | 可空，后续治理 |
| `business_type_code` | TEXT | 默认 `gallery_sale` | 支持后续版画、联名、代理销售细分 |

保留现有 `artwork_no`、`artwork_name`、`artist` 字段，原因是它们是销售发生时的文本快照，不能因为作品档案后来修改而丢失历史语境。

#### 3. 画廊匹配和库存规则

| 场景 | 规则 |
|---|---|
| 新增画廊销售 | 前端优先从作品档案选择作品，写入 `artwork_id`，同时写入编号、名称、艺术家、结算价快照 |
| 历史销售回填 | 优先按 `artwork_no` 精确匹配 `artworks.artwork_no`；不建议用标题 + 艺术家自动强匹配，只生成候选 |
| 库存扣减 | 只有 `artwork_id` 明确时，才自动更新 `artworks.sold_qty` 和状态 |
| 退款/作废 | 不直接删除销售记录，通过状态、退款金额和调整记录保留轨迹 |
| 作品档案修改 | 不重算历史销售快照；只影响后续销售默认值 |
| 多件版画或系列作品 | 使用 `sale_quantity`，成本按 `settlement_price_snapshot * sale_quantity` |

这个规则的目标是减少画廊销售的“文字相似就算同一件作品”的风险。画廊业务客单价高，宁可让少量历史记录进入待确认，也不要自动误配。

#### 4. 空间关联设计

空间使用应从“场地记录”升级为“空间项目 + 业务归属 + 到款事实”的结构。

建议在 `space_usage` 增加字段：

| 字段 | 类型建议 | 含义 | 兼容策略 |
|---|---|---|---|
| `business_type_code` | TEXT | 2.0 业务类型，如 `space_rental`、`brand_event` | 历史记录按 `type` 默认映射 |
| `cooperation_mode` | TEXT | 合作方式，如租赁、联办、赞助、置换、自营 | 可空，后续治理 |
| `project_owner` | TEXT | 项目负责人或对接人 | 可空 |
| `contract_no` | TEXT | 合同或合作编号 | 可空 |
| `business_status` | TEXT | 经营状态，如线索、洽谈、已签约、执行中、已完成 | 可由现有 `status` 映射 |
| `business_layer_code` | TEXT | 默认 `art_transaction_cooperation` | 特殊内部项目可人工调整 |

现有 `space`、`project_name`、`type`、`client`、`rental_type`、`receivable_amount`、`expected_payment_date` 继续保留，作为空间执行和财务管理字段。

#### 5. 空间业务类型默认映射

| `space_usage.type` 当前值 | 2.0 默认业务类型 | 业务层 | 备注 |
|---|---|---|---|
| 场地租赁 | 空间租赁 | 艺术交易与合作 | 标准租赁收入 |
| 长期经营 | 空间租赁 | 艺术交易与合作 | 可后续细分为长期合作 |
| 品牌快闪 | 品牌活动/企业合作 | 艺术交易与合作 | 需要记录合作方式 |
| 企业团建 | 品牌活动/企业合作或工坊/体验 | 默认艺术交易与合作 | 若以体验产品售卖，可人工归到体验活动 |
| 会议活动 | 空间租赁或品牌活动/企业合作 | 默认空间租赁 | 需结合客户和项目目的 |
| 沙龙 | 品牌活动/企业合作或工坊/体验 | 默认品牌活动/企业合作 | 自营公共活动需人工调整 |
| 展览 | 空间租赁或到馆参观支持项目 | 默认待确认 | 自营展览不应简单等同租赁收入 |

空间模块最容易出现“同一个空间既是运营场地，又是收入项目”的混合情况，因此不能只按空间名称判断业务类型。

#### 6. 收入、成本与利润视图关系

| 事实视图 | 画廊处理 | 空间处理 |
|---|---|---|
| `business_revenue_facts_v2` | 使用 `gallery_sales` 生成画廊收入事实，`gross_amount` 为成交价，`net_amount` 为扣佣金后净额 | 使用 `space_payments.payment_date` 生成到款事实，业务归属跟随 `space_usage.business_type_code` |
| `business_cost_facts_v2` | 使用 `settlement_price_snapshot * sale_quantity` 生成画廊结算成本 | 不自动生成空间成本，依赖 `expense` 项目映射或人工归属 |
| `business_profit_facts_v2` | 画廊净收入 - 作品结算成本 | 空间收入 - 明确关联的项目直接成本；共享运营成本暂不强行分摊 |

#### 7. 数据迁移和历史兼容

M2-06 迁移必须遵守低风险原则：

1. 先新增可空字段，不改原字段含义。
2. 先做只读匹配报告，列出可自动匹配、候选匹配、无法匹配三类记录。
3. 只有 `artwork_no` 唯一且精确匹配时，才允许自动回填 `artwork_id`。
4. 历史空间记录只做默认业务类型映射，不覆盖原 `type`。
5. 所有自动回填都要保留迁移脚本和回滚脚本。
6. 回填前必须备份生产表，并记录回填前后行数。

#### 1. 迁移总原则

M2 数据迁移采用“新增优先、只读先行、延迟回填、可暂停切换”的策略。

| 原则 | 含义 |
|---|---|
| 新增优先 | 优先新增表、新增可空字段、新增只读视图，不改旧字段含义 |
| 只读先行 | 先上线字典、映射表和 v2 事实视图，再考虑 2.0 前端流程 |
| 延迟回填 | 历史数据先生成匹配报告，经确认后再回填 |
| 不覆盖原文 | 不直接覆盖历史商品名称、支出分类、画廊文本和空间类型 |
| 可暂停切换 | v2 出问题先隐藏入口或停用 v2 视图使用，不影响 1.0 |
| 正式回滚有边界 | 只有影响原始数据、安全、权限、1.0 API 或核心录入时才触发正式回滚 |

#### 2. 迁移对象分组

| 迁移组 | 内容 | 风险等级 | 执行顺序 |
|---|---|---|---|

| C. 画廊与空间字段扩展 | `gallery_sales`、`space_usage` 增加稳定关联和业务归属字段 | 中高 | 第三批 |
| D. 只读事实视图 | `business_revenue_facts_v2`、`business_cost_facts_v2`、`business_profit_facts_v2` | 中 | 第四批 |
| E. API 白名单与只读守卫 | `server.js tableMap`、`READ_ONLY_TABLES`、角色读取权限 | 中高 | 与 D 同批验证 |
| F. 历史回填 | 商品别名、画廊 `artwork_id`、空间业务类型默认值 | 高 | 单独授权后执行 |

#### 7. 暂停与回滚分级

继续沿用前文已确认的三档机制，不把普通问题都升级为正式回滚。

| 等级 | 触发场景 | 处理动作 |
|---|---|---|
| 观察/修正 | 商品别名不全、支出映射不准、少量待归类、v2 展示字段需调整 | 记录问题，修正规则或视图，不影响 1.0 |
| 暂停切换 | v2 视图计算异常、2.0 页面报错、映射质量不达标、性能明显下降但 1.0 正常 | 关闭 2.0 入口或配置开关，保留原始数据和 1.0 使用 |
| 正式回滚 | 原始数据被污染、旧表不可用、1.0 核心录入失败、权限异常、生产 API 大面积失败 | 恢复代码回滚点，必要时恢复数据库备份 |

#### 8. 不触发正式回滚的情况

以下问题不应直接触发正式回滚：

- 文创或饮料别名仍需补充。
- 少量历史支出无法自动归类。
- 画廊历史销售无法自动匹配作品。
- 空间业务类型需要人工确认。
- v2 报表口径需要调整，但 1.0 页面和原始数据正常。
- 新增字段为空，等待后续治理。

这些问题进入数据治理清单，通过补规则、补别名、人工确认或暂停 v2 展示解决。

#### 9. 必须正式回滚的情况

以下情况必须进入正式回滚或紧急恢复：

- `revenue`、`expense`、`gallery_sales`、`space_usage`、`space_payments`、`creative_products`、`artworks` 等原始表发生非预期删除、覆盖或金额污染。
- 迁移导致 1.0 收银、支出、日结、画廊、空间或产品管理无法正常使用。
- 权限被意外扩大，未登录或 viewer 能写入/删除经营数据。
- `server.js` 白名单或只读守卫错误导致 v2 视图可被写入。
- API 容器无法启动，线上核心接口大面积失败。
- 数据库迁移锁表或性能问题影响正常营业录入。

#### 10. 回滚方式建议

| 对象 | 首选回滚方式 | 备注 |
|---|---|---|
| 前端 2.0 入口 | 恢复上一版静态文件或关闭配置开关 | 优先使用暂停切换 |
| `server.js` | 恢复发布前备份并重启 API 容器 | 涉及权限时必须复测 |
| v2 只读视图 | `DROP VIEW` 或恢复上一版视图定义 | 不影响原始表 |
| 新增表 | 暂停使用优先；正式回滚时可 `DROP TABLE` | 若已有人工作业数据，先导出 |
| 新增可空字段 | 通常可保留不用；正式回滚需先确认无依赖 | 避免为回滚而制造新风险 |
| 历史回填 | 使用回填前备份值或完整库备份恢复 | 回填必须单独留前后快照 |
| 原始数据污染 | 从生产备份恢复或按修复脚本回滚 | 必须单独授权和记录 |

## 十三、文档变更防错机制

为避免后续开发文档再次出现章节重复、口径分裂、计划与任务卡互相冲突等低级错误，2.0 文档从本节开始执行固定的变更防错机制。

### 适用范围

凡是修改本开发文档、M1 输出文档、数据库设计文档、迁移方案、回滚方案、任务卡或阶段验收记录，都必须执行本机制。

### 写入前检查

每次写入前，先确认本次变更属于哪一种：

| 变更类型 | 处理规则 |
|---|---|
| 补充 | 只能补到已有章节的对应位置，不新建重复章节 |
| 修正 | 必须说明替换了哪一段旧口径 |
| 新增 | 必须确认现有文档中没有同主题章节 |
| 阶段冻结 | 已确认口径不得直接改写，变更先进入待确认清单 |

写入前必须检查：

- 是否已有同名或同主题章节。
- 是否已有同一任务编号、同一模块编号或同一阶段计划。
- 新内容应归入现有章节，还是确实需要新增章节。
- 新内容是否会改变已确认口径、阶段边界或回滚逻辑。

### 写入中规则

- 同一个主题只能有一个主位置。
- 任务卡、阶段目标、任务计划和下一步不得分散到多个并列章节。
- “下一步”只写当前推进动作，不承载详细计划。
- 已确认的业务模型、数据安全原则、回滚逻辑，如需调整，必须标注为“待馆长确认变更”。
- 新增二级或三级任务时，必须挂靠到已确认的一级模块下。

### 写入后检查

每次写入后必须做一次文档自检：

| 检查项 | 通过标准 |
|---|---|
| 章节唯一性 | 不存在同主题重复章节 |
| 编号连续性 | 一级标题编号顺序清楚，没有跳号或重复编号 |
| 口径一致性 | 新内容不与已确认业务模型、数据安全原则、回滚逻辑冲突 |
| 任务归属 | 新任务能明确归入 M1-M6 中的一个模块 |
| 下一步清晰 | 文档末尾只保留一个明确下一步 |

### 交付回报要求

每次修改本开发文档后，回报时必须说明：

- 改了哪些章节。
- 是否改变业务口径。
- 是否改变开发范围。
- 是否发现与原文冲突。
- 是否有待馆长确认事项。

### 冲突处理

如果发现新内容与原文存在冲突，先按以下顺序处理：

1. 标记冲突位置。
2. 说明冲突类型：结构重复、口径冲突、范围扩大、阶段错位或验收标准不一致。
3. 提出修正方案。
4. 经馆长确认后再写入。

低风险的结构修复可以直接执行，但必须在回报中明确说明“未改变业务口径”。
