## 2. Go/No-Go 顺序

1. 确认 M6-08 已授权、窗口和三名责任人已填写。
2. 从干净 Git 提交运行 `npm run check:m6-release`，保存版本、提交、迁移数和清单哈希。
3. 只读记录当前生产版本、容器状态、数据库版本、灰度值及 P0/P1 数量。
4. 运行 `bash scripts/backup-db.sh`。必须同时得到 dump、dump SHA、基线 JSON、基线 SHA 和 manifest。
5. 在备份目录执行两个 SHA 校验，并执行 `pg_restore --list`。任一失败立即 No-Go。
6. 将该 dump 恢复到隔离数据库，比较表/视图数量、结构指纹、核心表记录数、金额汇总、最新事实日期和灰度值；隔离库完成后删除。
7. 复核正向清单为 20 个迁移、回滚清单为 16 个文件，且 SHA 全部匹配。
8. 只有上述项目全部通过，才可进入迁移阶段。

## 3. 迁移与校验

1. 迁移期间保持 `operations_rollout=off`，停止新的发布操作并记录开始时间。
2. 严格按 `sql/m6-forward-manifest.json` 顺序执行尚未应用的追加迁移；每个文件使用 `psql -X -v ON_ERROR_STOP=1`，失败立即停止。
3. 不重复执行初始化基线，不覆盖收入、支出、画廊、空间、收款、日结等原始事实。
4. 迁移后只读检查 28 个业务维度、9 张 M3-M6 必要表、19 个 2.0 视图、迁移状态、灰度仍为 `off`、未复验 P0/P1 为 0。
5. 运行 M6 权限矩阵和自动对账；所有金额按分精确比较，差异必须能定位来源表、来源 ID、明细键和影响金额。
6. 迁移验证通过后才构建并启动 API/静态服务。`db` 与 `/healthz` 必须健康，Nginx 首页必须返回 200/301/302。
7. 保存部署后版本、容器状态、健康结果、只读对账结果和结束时间。M6-08 不打开 2.0 入口。

## 4. 停止条件

出现以下任一项立即停止：备份或基线校验失败、隔离恢复不一致、迁移校验和不匹配、SQL 执行错误、原始事实变化、未授权写入、敏感信息暴露、1.0 核心流程不可用、出现未复验 P0/P1、金额出现不可解释差异。

## 5. 回退顺序

1. 保持或恢复灰度为 `off`，停止继续迁移和放量。
2. API/静态异常时先切回执行记录中的上一提交或镜像，再验证 1.0 登录、收入、支出、日结和只读查询。
3. 本阶段迁移均为追加结构。事故处理中默认保留已追加结构，避免为回退代码而删除数据结构。
4. 只有数据库已损坏且无法通过前向修正恢复时，才评估整库恢复。整库恢复会覆盖备份点后的生产写入，必须另行取得明确授权、冻结写入并记录数据损失窗口。
5. 使用本次已验证的 dump 恢复后，重新比较对应基线并复核 1.0 核心流程；未通过不得恢复服务。
