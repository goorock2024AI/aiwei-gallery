# 交付流程入口

这是运营数据管理系统优化、修复、上线和排障的唯一默认入口。目标是先做初步分级和路由，再只读取必要文件。

## 1. 初步分级

每次先判断任务等级，再进入分析：

| 等级 | 任务 | 执行方式 |
|---|---|---|
| L0 | 咨询、评估、流程讨论，不改文件 | 只讨论结论，不强制六步记录 |
| L1 | 小文档修改、样式微调、单点前端修复 | 压缩闭环：目标、改动、验证、记录 |
| L2 | 常规功能优化、多个文件改动、前后端联动 | 完整闭环，记录可简写 |
| L3 | 部署、数据库、权限、财务、生产写入 | 完整闭环，必须有授权、回滚和证据 |

方向型任务先问清真实目标。例：“优化数据看板”不是目标；目标应说明使用者要借助看板获得什么经营判断或感知能力。

## 2. 路由

每次先归类，再选对应流程。

| 类型 | 触发 | 读取 |
|---|---|---|
| 前端静态热修 | 只改 `app/index.html`、`app/css/*`、`app/js/*`，不改写生产数据 | `references/runbook-frontend-static-hotfix.md`、必要时 `references/runtime-facts.md` |
| 后端 API 热修 | 改 `server.js`、REST 白名单、上传接口、后端转换逻辑 | `references/minimum-verification-matrix.md`、`references/runtime-facts.md`、必要时部署方案 |
| 数据库/财务变更 | 建表、改列、迁移、退款、作废、删除、生产数据修复 | 治理规则、相关 SQL、白名单、`references/minimum-verification-matrix.md` |
| 线上排障 | 页面异常、API 502、登录失败、数据不一致 | 先读 `runtime-facts.md`，确认事实后再决定是否读其他文件 |

升级规则：涉及权限、密钥、退款/作废、删除、数据库迁移、生产数据写入时，直接升级为“数据库/财务变更”。

## 3. 上下文读取

默认只读：

- 最新相关开发日志段落。
- 目标文件。
- 本文件指向的对应文件。

仅在以下情况读长文档：

- 部署事实不足：读 `runtime-facts.md`。
- 历史踩坑相关：读 `deployment-gotchas.md`。
- 深度运维或架构背景：读部署方案。
- 后端、数据库、权限或生产写入：读系统事实、SQL、白名单和治理规则。
- 验证失败：回到分析，补读相关历史日志。

## 4. 文件职责

- `runbook-frontend-static-hotfix.md`：前端静态热修动作。
- `minimum-verification-matrix.md`：各类任务最低验证标准。
- `runtime-facts.md`：唯一默认运行事实源。
- `deployment-gotchas.md`：部署踩坑记忆。
- `release-checklist.md`：兼容索引，不作为默认流程入口。

## 5. 验证节制

同一事实只用一种稳定方式验证。只有结果异常时才加第二种方式复核。

例：静态文件已用 HTTPS token 验证 200 和字节数后，不再同时用多个命令重复拉取同一 URL。

## 6. 记录标准

- 开发日志只记录改动、验证摘要、回滚点、边界和状态。
- 不复制完整命令输出。
- 任务完成时保留与等级匹配的闭环痕迹；低开销压缩表达，高风险完整记录。

## 7. 完成标准

按任务类型满足 `minimum-verification-matrix.md`，并在日志中记录可回溯证据。
