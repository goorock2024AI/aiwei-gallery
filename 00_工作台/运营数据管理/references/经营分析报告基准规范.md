# 经营分析报告基准规范

规则版本：1.0.0。状态：结构与口径初版；月报章节和专项方法在真实使用中修订。适用于“经营分析报告”板块，统一约束数据、计算、分析、格式、发布与修订。此文件是唯一基准；Skill 引用它，不另存一套规则。

## 1. 报告类型与入口

- 周经营分析报告：按周一至周日完整周，采用《周经营分析报告标准版.md》。报告中心接入weekly类型、五项核心数据及标准版附录；最新版本与历史版本可筛选，跨月周在覆盖月份中可检索。接入代码于2026-10-17部署上线并通过健康/静态/权限检查；真实周报独立通过正式后台发布，不能将代码部署视为报告已发布。正式发布沿用管理员、来源包及修订链要求。

- 月度运营分析报告：一个完整自然月，默认比较上一个完整自然月；每月用户通过 Codex 发起，系统不自动定时调用模型。同月再次发布使用修订，保留原版。
- 专项分析报告：用户指定经营问题、期间与比较方式；通用要求一致，针对问题形成任务说明。不存在客户身份关联时，同日销售不能当作某票种客户的购买转化。
- 所有已登录且完成账号验证的平台用户可阅读和下载已发布报告。数据包及核对工具维持原运营权限，后台发布仅管理员。草稿为 Codex 工作产物，发布前不进入报告目录。
- 目录按报告类型、经营月份、主题搜索及分页检索。修订版和历史版可追溯。读取 HTML 或下载均须验证平台身份；下载后的文件可离线阅读。

## 2. 经营口径

到馆人次=当日普通票数量+套票数量；一套票一人入馆、一杯咖啡权益。人数是人次，未登记免费访客未覆盖。缺数量时保留已记录数量，完整人数、人均与销量密度标不可计算。

四项=咖啡套票、非饮料文创零售、工坊、线下画廊。套票收入完整计入一次，单售咖啡及空间合作不进入四项。完整已归属馆内收入另含普通票、单售咖啡与饮料；空间合作独立。画廊目前依据馆长确认视为到馆收入，未来启用线上渠道时须修改数据记录与规则版本。

商品按后台业务分类与饮料标记汇总。饮料名称疑点只提示复核，不擅自修改主数据；名称剔除或合并别名若用于报告，列明具体清单、理由、影响与暂定性质。未命名及分类不明保留异常，不能当可靠选品排行。

销量是件/套/消费次数，不能称购买人数或交易单数。每百人销量=数量/到馆人次×100；没有订单或购买者记录时避免“真实成交人数转化率”。咖啡权益不是核销出杯量。

## 3. 计算与完整性

应用在同一快照中取本期与比较期，保存逐日、业务类型、单品、成本覆盖、费用、待归属退款及来源指纹，计算后封存 SHA256。程序输出 metrics，不依赖模型心算。

- 人均收入=已归属馆内收入/完整到馆人次；四项人均另列，不能替代全馆口径。零人数或人数不全时返回 null。
- 环比=(本期-比较期)/比较期；基期非正或缺失时不可计算，展示绝对变化；月长不同另列日均，营业日未知明确说明。
- 销售毛利=收入-已售项目的可信直接成本；采购支出不是当期销货成本，费用不是销售毛利。缺成本保留“已覆盖部分毛利”，完整毛利返回 null。
- 四项毛利贡献率=项目完整销售毛利/四项完整毛利之和；存在缺成本、待归属退款或合计非正时不可计算。无流水不自动补“已确认零经营”。
- 收入变化拆解固定采用先客流后人均：客流项=(本期人次-前期人次)×前期人均；人均项=本期收入-本期人次×前期人均。注明顺序与算术性质，不称因果。
- 指标均附来源范围与质量缺口；未知成本不补零、不推测实际核销、缺少经营背景时降低结论强度。

## 4. 分析问题与证据需求

| 必答问题 | 必要数据 | 当前缺失时的处理 |
|---|---|---|
| 客流与人均变化 | 票种数量、各收入、比较期 | 缺人数时仅报告已知收入与记录数 |
| 套票价格及票咖结构 | 生效日、成交价、票种、单售咖啡、成本、经营背景 | 没有对照或身份关联，只分析结构与同步变化 |
| 哪项销量受影响 | 销量、人次、营业/可售安排 | 分开算术拆解与实际原因 |
| 文创选品 | 单品数量、收入、成本、库存、可售天数 | 缺库存不能区分缺货与需求不足 |
| 工坊表现 | 销量、开课场次、容量、取消记录 | 先列供给信息缺口 |
| 毛利与贡献 | 本期及前期可信直接成本、归属退款 | 展示覆盖部分与缺口，暂停完整比较 |

先核对需求，再判断哪些数据可读取、可计算、需新增记录。当前不具备库存日序列、工坊容量日历、实际咖啡核销和购买身份关联；这些属于未来记录需求，不从现有数据反推补造。

## 5. 月报标准与专项方法（初版）

月报顺序：结论摘要；数据范围与质量；客流与整体人均；票种与咖啡结构；文创/工坊/画廊及单品变化；毛利及成本缺口；上期行动复核与本期验证计划。结尾列具体行动和衡量指标。每节回答问题并引用指标，数据不足时解释不可判断及补证需求。

专项任务说明包含：支持的经营决策、对象、期间、策略生效日、比较方法、经营背景、假设、验证指标、缺失证据。分析顺序：质量检查→变化与拆解→假设与证据→判断边界→行动。专题可以调用月报的共同分析步骤，不机械套入全部月报章节。

区分数据事实、算术拆解、可能解释、建议及待核实事项。不能为填满章节输出缺证据的结论。行动要求写明检查/试验事项、衡量指标和下一期复核内容；未提供上期行动时写“未取得”，不宣称已实施。

## 6. HTML与发布、修订

### 6.1 展示规范（2026-10-11确认，版式1.0）

采用已确认的报告样稿，复用 web-design-engineer 的排版方法：深绿文字与暖白背景、金色小标题，桌面标题40px、正文17px、行距1.9；手机标题29px，内容留白20px。正文阅读宽度约72个字符，章节分组、短段落，避免整篇长文连续铺排。

阅读顺序：报告类型/期间/版本→标题→结论摘要→到馆/已归属收入/每人次收入/完整毛利四项指标→业务收入比较表→详细分析→行动与衡量指标→来源与限制。指标及表格由程序从保存的来源快照生成；无来源支持时省略，不从正文猜数字。环比基期无效时注明不可计算，缺完整成本时显示不可计算，无流水用“—”并说明。原零售分类与纯文创区分，分类疑点和待归属退款就近提示。

桌面提供侧栏章节目录，手机目录自然排列，不增加强制交互。在线阅读与下载HTML使用同一模板，下载文件内含样式，不依赖外部字体、网络脚本或图片。打印隐藏目录与操作按钮，保留标题、期间、分析、来源；支持浏览器另存PDF。所有内容转义，目录使用程序生成的固定锚点。

样式调整不修改历史正文、报告版本、规则版本或来源快照；展示计算版本单独注明。新的分析判断、分类修正或成本补齐须按修订流程发布。月报与专项共享视觉规范，专项仅呈现其问题所需的内容，不为了版式补造数据。

### 6.2 发布与修订

Codex 生成结构化报告：packetId、reportType(monthly/special)、topic、ruleVersion、title、summary、sections[{title,body}]、actions[{action,measure}]，修订加 supersedes。后台校验身份、来源、版本与月度范围，渲染成自包含 HTML；正文以文本转义，不能执行上传 HTML 脚本。提供独立阅读页、HTML下载及浏览器打印/PDF。

发布前核对来源SHA、计算版本、事实与解释边界、规则版本、必要章节及行动。用户授权发布后通过正式后台写入，身份由服务端记录。未授权发布时保存草稿。发布失败保留草稿及错误，不绕过权限。专项目标未明确时先澄清关键问题，继续可独立的数据检查。

修订使用新记录、自动递增版本、关联上一版；同月重复月报要求修订，已经有修订的旧版本不能再分叉。旧报告保留来源，不随业务数据变化重算。历史rc.14报告标历史口径，不伪装使用本版规则。

## 7. 静态报告与月报支持归档（2026-10-21确认）

Agent负责经营分析与撰写，程序负责取数、计算、校验和发布。发布结果由三部分组成：云端数据库中的封存经营快照、结构化分析/行动记录，以及云端私有持久化卷中的自包含HTML。HTML生成一次并记录SHA，不在每次阅读时重算历史报告；平台登录后读取及下载同一文件，不能将内部经营报告放到公开uploads目录。

月报取数仍按完整自然月实时计算，同时读取weeklyReviews或`GET /rest/v1/operations-reports?monthContext=YYYY-MM`取得期间重叠的最新周报，回顾历史判断、待验证原因、行动和数据缺口。跨月周保留完整分析并标记，月度指标不通过周报合计相加得到。

后台网页发布仍限管理员；馆长明确授权的历史报告可通过服务器SSH部署通道执行`scripts/archive-weekly-deployment.js`，使用真实release SHA及独立deployment服务主体留审计，不创建账号、不伪造平台登录。部署前逐份核对全部封存来源SHA及实时本期/比较期指标，任何变化停止整批导入。相同输入可重复执行复用，修订保留历史。该通道是正式维护工具，不是未经授权的直接SQL操作。发布包保留在私有备份目录，不入Git；报告卷与数据库必须共同备份，应用回退保留归档与后续经营数据。
