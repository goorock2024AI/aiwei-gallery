## 基线与范围

实施分支 `codex/artist-library`，由本地已有rc.34发布记录提交 `d57a1fe`建立独立工作区；没有搬入原2.0开发区的未提交工作，也没有重新核验生产active SHA。候选版本 `2.0.0-rc.34-artist-manual.1`。发布前必须重新核对届时的生产基线。

需求与两张设计图位于资料入口仓的 `aiwei-planning/`，以需求v1.1、录入图v2为准。实现保留现有运营后台外壳，新增艺术家模块，不替换全局品牌或其他业务入口。

已实现：

- 艺术家新建、编辑、详情、分页搜索与关系/跟进状态筛选；同名档案分开保存；管理员归档和恢复。
- 姓名/艺名和来源必填；联系方式、简介、所在地、媒介、标签、负责人、履历及内部备注可后补。
- 外部URL单框录入，中英文逗号或换行分隔，验证HTTP/HTTPS、去空项和完全重复项，保留参数及片段；含字面逗号的URL使用编码形式`%2C`。
- 实际文件流式上传、暂存、与档案一起确认关联、私有下载；PDF和常见图片预览，DOC/DOCX及ZIP下载。文件原名、分类、大小、校验值和操作来源留痕。
- 关联现有作品，不改写原艺术家文本、价格、库存及成交；独立记录投稿作品线索，未知报价留空。
- 手动登记多次投稿、邮件主题/正文/发件人/来源邮箱/邮件与线程标识、对应附件；追加跟进和下一步日期。
- 乐观并发检查、创建/追加记录幂等、防同名覆盖、异常反馈、取消暂存、过期暂存及中断文件清理。

本阶段未实现邮箱读取、自动收集、批次归档、历史补录、外部大附件链接自动下载及对外邮件发送。界面登记原始投稿的入口在保存档案后的“投稿与跟进”中，未显示不可用的邮箱选择器。

## 数据与接口

新增四表：`artist_profiles`、`artist_files`、`artist_artwork_links`、`artist_records`。艺术家扩展资料放在受字段校验的JSONB中；文件状态为staged/active/removed，投稿与跟进记录保留追加历史。通过专用API访问，不将新表加入通用REST写表白名单。

| 接口（前缀 `/rest/v1/artist-library`） | 行为 |
|---|---|
| GET / | 分页查询，q/relation/status/page，管理员可看archived |
| POST /、GET/PATCH /:id | 建档、详情、带version更新；客户端生成稳定创建编号 |
| GET /options | 当前可选负责人、关系、状态和单文件限额 |
| POST /files?name=…&category=… | 原始文件流上传，返回暂存编号；不使用Base64 |
| GET /files/:id | 已登录读取，preview=1允许PDF/图片内联；暂存仅上传人可读 |
| DELETE /files/:id | 上传人放弃尚未关联的暂存文件，后续清理 |
| GET /artworks?q=… | 选择现有作品候选 |
| POST/DELETE /:id/works | 关联/解除关联，不改原作品业务事实 |
| POST /:id/records | 增加投稿、跟进或投稿作品线索，关联本档案附件 |
| POST /:id/archive | 管理员按版本归档/恢复；不物理删除材料 |

viewer只读；editor和admin可录入；归档恢复仅admin。服务端逐接口校验，不能通过直调接口绕过按钮限制。文件不挂载到Nginx公共目录；新静态路径边界检查防止读取应用根目录以外的资料。

## 本地运行与验证

`npm ci`安装含浏览器测试的开发依赖；生产镜像仍使用`npm ci --omit=dev`。专项命令：`npm run check:artist-library`。

专项测试要求本机PostgreSQL17、Edge及已存在的隔离测试模板；连接配置从被忽略的`tmp/m3-05-test.json`读取，并强制检查127.0.0.1:55435。每次创建独立克隆和独立恢复库，结束后释放；不对模板写业务数据。`PG_BIN`可指定PostgreSQL工具目录。测试原始记录、样本、数据库备份及截图均在忽略目录`tmp/artist-library/`，不提交真实资料或凭据。

本轮留有本地演示地址 `http://127.0.0.1:3160/preview-entry`，独立数据库、虚构艺术家与示例PDF；演示入口由忽略目录中的临时辅助服务提供，不包含在产品和发布包中。本地服务重启/关闭后需重新启动演示助手，不能将此地址当作正式系统。

## 存储、迁移与发布条件

- `ARTIST_FILE_DIR`：生产必须显式配置持久私有目录；仓库Compose候选使用API独占卷 `/artist-files`，不挂载给Nginx。模块拒绝将文件目录设在app或公共uploads之内。
- `ARTIST_MAX_FILE_BYTES`：本地默认200MiB，已验证150MiB级传输。生产需同时核对API、Nginx、外层HTTPS网关和可用容量；本轮没有验证线上多层代理。
- `ARTIST_LIBRARY_ENABLED=false`：关闭专用API写读入口，便于回退；正式发布时需同步控制菜单入口。
- `ARTIST_STAGED_RETENTION_DAYS`：清理脚本默认7天，仅清理过期且未关联的暂存/已放弃文件及过期`.part`；不清理已关联文件。脚本未安装为定时任务。
- 升级使用专项幂等迁移 `sql/20261103_artist_library.sql` / `node scripts/artist-library-migrate.js`；没有将迁移擅自接入现有共享发布自动钩子。新表也已补入初始化SQL。
- 上线交接仍需落实共享发布配置中的私有卷、外层上传限额、备份范围、执行专项迁移和健康检查；仓库历史Compose不是当前共享发布服务的运行事实源。

备份必须同时覆盖四表、关联作品事实源及私有文件；恢复先确保作品主档案存在。专项测试已真实导出四表、恢复到另一隔离库、复制私有文件，再通过API下载并核对原始字节。

回退时先停人工写入和后续导入，隐藏入口或停用API，恢复上一兼容应用，保留四表、操作日志和全部已关联文件，不整库覆盖、不自动删投稿。若已产生新资料，不以撤销表结构作为回退方式。
