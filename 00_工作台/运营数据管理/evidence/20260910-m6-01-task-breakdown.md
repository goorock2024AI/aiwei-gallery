- 分支：`codex/operations-v2`
- 输入：M1/M2 冻结口径与迁移安全方案、M3/M4/M5 阶段评审
- 边界：本任务只做任务拆分和准入冻结；未连接生产、未备份生产库、未迁移、未治理真实历史数据、未部署或切换入口

## 结论

M6 拆分为 M6-02 至 M6-10 九个任务包，按“新库迁移重放→代码/安全回归→1.0/2.0 对账→灰度开关→试运行观测→生产前置包→生产追加迁移→内部试运行→切换评审”执行。M6-02 至 M6-07 可在本地或不连接生产的受控环境内继续；M6-08 起每个生产阶段必须在具体产物可审查后取得单独授权。

## 对账口径

M6 不用“1.0 合计必须等于 2.0 所有合计”作为粗略标准，而是按事实类型建立可解释等式。

| 对账对象 | 通过标准 |
|---|---|
| 收入 | 1.0 原始净收入 = 2.0 已归类收入 + 待归类收入 + 经明确规则识别的口径差异；每个差异必须可定位来源表、ID 和明细键 |
| 期间支出 | 1.0 `expense` 金额与 2.0 `period_expense` 事实分开核对；销售成本和画廊结算成本不重复与期间支出合并对比 |
| 销售成本 | 通过销售快照、数量与单位成本逐行复算；缺成本项保留在治理清单 |
| 画廊与空间 | 成交、结算、应收和到账分别对账，不把不同时点字段强行相等 |
| 日结 | 已保存的 1.0 日结值、快速结存计算和对应原始收入不因 2.0 视图或入口而变化 |
| 原始事实 | 迁移和试运行前后核心表行数与金额快照一致；受控新增业务记录必须单独标识 |

金额以数据库 `NUMERIC` 精确到 0.01 元对账，不使用百分比容差掩盖差异。行数、状态和来源关联应精确一致；只有进入有名称、有依据、有影响金额的差异解释集，才可视为已对账。

## 灰度开关和角色

| 模式 | 入口 | 用户范围 | 用途 |
|---|---|---|---|
| `off` | 隐藏 2.0 运营管理入口 | 无 | 生产迁移后默认状态、暂停切换 |
| `admin` | 显示试运行标识 | 仅 admin | 首轮管理员只读验证 |
| `staff` | 显示试运行标识 | admin + editor | 内部试运行 |

- viewer 在 M6 仍不能进入含成本、利润和治理明细的 2.0 页面。
- 开关变更只允许 admin，必须记录操作人、原值、新值、时间和原因。
- 前端入口和直接 URL 都要受开关与角色限制；敏感 API 继续以服务端角色矩阵为最终边界。
- 开关关闭只暂停 2.0 入口，不删除追加结构，不修改 1.0 页面。

## 阶段门槛

| 门槛 | 通过条件 | 失败处理 |
|---|---|---|
| G0 本地发布候选 | M6-02 至 M6-06 通过；新库重放、回归、对账、开关和观测可用 | 修正后重验，不准备生产执行 |
| G1 生产前置 | M6-07 通过；备份可恢复、基线可复核、runbook 与回退点完整 | 保持本地状态，不申请生产迁移 |
| G2 生产只读 | M6-08 通过；迁移只追加、1.0 正常、权限正常、入口 `off` | 暂停或按触发条件回退，不开始灰度 |
| G3 内部试运行 | M6-09 完成预定观察周期；无 P0/P1，对账和性能达标 | 开关回到 `off`，修正后重新计时 |
| G4 切换决策 | 技术验收、业务验收和回退准备均有记录，馆长确认范围和时间 | 保持内部灰度或 `off`，不自动正式切换 |

## 试运行问题分级

| 级别 | 示例 | 处理 |
|---|---|---|
| P0 | 原始数据污染、未授权写入、敏感信息暴露、1.0 核心流程不可用 | 立即停止，入口 `off`，进入正式回退/恢复评估 |
| P1 | 核心金额无法对账、角色越权、大量 API 失败、性能影响营业 | 暂停试运行，修正并完整复验后重开 |
| P2 | 局部视图/页面失败、可解释的候选差异、交互阻碍 | 可在开关范围内观察修正，设定负责人和截止时间 |
| P3 | 文案、样式、非关键体验 | 记录并排入普通修正 |

## 通用完成定义

1. 完整前向迁移链可从全新隔离库重放，文件顺序与校验和固定，不依赖旧测试库的隐式状态。
2. 收入、期间支出、销售成本、画廊、空间和日结按冻结等式对账，金额精确到 0.01 元，每个差异可追溯。
3. 未登录、viewer、editor、admin 的服务端和前端权限均通过；RLS 关闭现状在线上验收中持续作为 P0 风险。
4. 1.0 收银、支出、日结、商品、画廊和空间流程在迁移和试运行前后均可用，原始事实不被覆盖。
5. `off/admin/staff` 三档开关由 admin 受控变更，关闭后 1.0 仍可独立使用。
6. 试运行问题有级别、证据、影响、负责人、修正版本和复验结果；P0/P1 未关闭不得进入下一门槛。
7. 生产任务执行前具有当时的备份、基线、回退点、执行窗口、负责人和明确授权；超出已审批阶段必须停止。
8. M6 只验证和启用 2.0 已冻结能力，不引入 CRM、预测、经营评分或 3.0 驾驶舱。

## 授权矩阵

| 动作 | M6-01 授权是否覆盖 | 执行条件 |
|---|---|---|
| 本地代码、脚本、新库演练、自动测试和文档 | 是 | M6-02 至 M6-07 可按任务顺序执行 |
| 只读连接生产库并导出基线 | 否 | M6-08 前提交具体查询、范围、产物路径和隐私边界，单独授权 |
| 生产 `pg_dump`、恢复验证或数据库迁移 | 否 | 备份命令、存储位置、校验方式、回退点可审查后单独授权 |
| 生产部署或重启 API | 否 | 发布包、变更清单、回退命令和执行窗口可审查后单独授权 |
| 开启 `admin`/`staff` 灰度 | 否 | M6-08 通过、观察周期和负责人已确认后单独授权 |
| 真实历史治理批次或回填 | 否 | 候选、影响预览、审批、应用和撤销单独留证 |
| 将 2.0 宣布为正式入口 | 否 | M6-10 技术评审后由馆长作业务切换决定 |

## 主要风险与处理

| 风险 | 级别 | 处理 |
|---|---|---|
| 长期复用测试库导致迁移遗漏 | P0 | M6-02 必须从新库重放并校验迁移清单，不以现有测试库作为通过证据 |
| RLS 关闭、安全依赖 Node API | P0 | 每道门槛验证未登录和三角色，敏感视图写入必须 405 |
| 1.0 与 2.0 属于不同业务口径被误判为错账 | P1 | 使用分类等式和差异解释集，不直接比较不同含义的总数 |
| 只隐藏前端菜单却可直接进入 | P1 | M6-05 覆盖导航、路由、开关配置写入和服务端权限 |
| 试运行修正边运行边扩大范围 | P1 | 开关升级只能 `off → admin → staff`，每次升级需新的证据与授权 |
| 把技术试运行当成业务验收 | P1 | M6-10 分开记录技术结论和馆长的业务切换决定 |
